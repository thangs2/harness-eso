# Câu hỏi kiến trúc sản phẩm phải trả lời

**Phục vụ:** Goal G-B · **Phép thử vision:** V1
**Đo:** 2026-10-24 trên một consumer thật (hệ microservices qua RabbitMQ). Consumer chỉ là **mẫu đo**; phát
biểu dưới đây là về **sản phẩm**.

## 1. Ba câu hỏi

Sản phẩm phải trả lời được ba câu này từ dữ liệu của chính nó, không cần grep, không cần người đọc code:

| # | Câu hỏi | Đúng khi |
|---|---|---|
| R1 | **Ai consume routing key `K`?** | danh sách service + handler, **kể cả** consumer đăng ký bằng wildcard mà key đó khớp |
| R2 | **Đổi schema payload của route `R` thì ai ảnh hưởng?** | đi hết `route → payload → handler → service`, và **tách riêng** những consumer sẽ gãy **im lặng** (wildcard, không type check) |
| R3 | **gRPC method `M` gãy thì ai chết?** | blast radius qua client/service dùng nó |

R2 là câu quan trọng nhất: với wildcard, **không có type system nào bắt lỗi** cho consumer, nên một lần đổi
tên field sẽ chạy qua mà không ai biết cho tới khi production.

## 2. Vì sao tool hiện có không trả lời được

Đây là phần **phải** ghi lại, vì nếu không thì phiên sau sẽ có người đề xuất "dùng codegraph đi".

### 2.1 Config không phải graph

Hệ thật khai listener ở **hai** tầng khác nhau:

```jsonc
// config — "listener" thực chất là WILDCARD (phạm vi binding)
"listenedMessageRoutes": {
  "booking.lifecycle.event": { "routingKey": "booking.*.*.event", "channels": ["booking.lifecycle"] }
}
```

Nhưng handler thật đăng ký **key cụ thể**:

```ts
// ~482 handler, đăng ký theo pattern cụ thể
@ExternalMessageHandler(PostCreatedBridgeEvent.PATTERN)   // 298 chỗ dùng X.PATTERN
@ExternalMessageHandler('tenant.position.updated.event')   // ~184 chỗ dùng literal
```

⇒ Một graph dựng từ config sẽ có **~20 edge wildcard béo** và **sai về mọi thứ cụ thể**. Nó không trả lời được
R1 (ai consume key `K`), vì `K` không xuất hiện trong config.

### 2.2 Subscription không nằm ở chỗ handler

Routing key thật nằm ở **file khác**, sau một hằng số:

```ts
// cqrs/events/post.bridge.event.ts
export class PostCreatedBridgeEvent extends MsxBaseEvent<any> {
    static readonly PATTERN = 'byngo.post.created.event';   // ← key thật ở đây
}

// controllers/post.listening.controller.ts
@ExternalMessageHandler(PostCreatedBridgeEvent.PATTERN)     // ← handler ở file này
```

⇒ `grep 'byngo.post.created.event'` tìm được **một** file — file khai hằng số, **không** phải file đăng ký
consumer. Muốn trả lời R1 phải: resolve symbol `X.PATTERN` → literal → glob-match với key hỏi, trên toàn bộ
handler của mọi service. Đó là **graph traversal**, không phải text search.

### 2.3 Fan-out nằm trong code, không nằm trong config

Config có mô tả tay *"Consumed by mu-analytics"* trong trường `description`, nhưng tập consumer **thật** được
quyết bởi ~482 pattern với glob, trên nhiều service. Đây đúng là loại câu hỏi cần graph (fan-out), và đúng là
loại mà grep không làm được.

### 2.4 Đó là hệ thống tự sửa topology ở runtime

Hệ có registry sống: `ENABLE_TOPOLOGY_SYNC`, `FUSION_REGISTRY_URL`, `topology.discovery.announced.event`,
`fusion.topology.updated.event`. Nghĩa là **nguồn sự thật cuối cùng không phải file**.

⇒ Sản phẩm **phải** ghi **provenance** trên mỗi edge: `declared` (khai trong config) · `derived` (suy ra từ
code) · `runtime` (registry báo). Không có cột đó thì khi graph sai, không ai biết sai ở tầng nào.

## 3. Hệ quả lên thiết kế

Graph phải có **sáu loại node, bốn loại edge**, và indirection là trung tâm:

```
Publisher(service) --declares--> Route(routingKey) --bound-to--> Exchange
Route(routingKey)  <--globs--   HandlerPattern     <--registered-by-- Consumer(service)
HandlerPattern     --resolves-via--> EventClass.PATTERN   (indirection codegraph bỏ sót)
Route(routingKey)  --carries--> PayloadSchema
Service            --rpc-->     GrpcMethod(proto)
```

Ba câu R1–R3 trở thành **traversal**, không phải grep.

## 4. Số đo mẫu (2026-10-24)

Trên một consumer thật, để biết quy mô thật của bài toán — không phải con số marketing:

| Số đo | Giá trị |
|---|---|
| Service | 27 |
| Exchange phân biệt | 27 (khai 183 lần — mỗi service tự khai bản sao) |
| Route công bố | 273 |
| Listener khai | 179 — **gần hết là wildcard** |
| Handler thật | ~482 (298 dùng `X.PATTERN`, ~184 literal) |
| gRPC | 1 service, 2 RPC |
| REST giữa service | 0 (giao tiếp hoàn toàn qua message bus) |

## 5. Cách tiến hành: **deep dive coding**, không thảo luận thiết kế

**Chốt 2026-10-24** (operator): bài toán này *"cần phải deep dive coding, sẽ rất heavy task to discussion"*.

Nghĩa là bước tiếp theo **không** phải một buổi bàn thiết kế. Nó là: viết resolver, chạy trên dữ liệu thật,
đưa ra output để soi. Mọi câu hỏi thiết kế còn lại (graph store thế nào, expand wildcard hay không, output
JSON hay text) chỉ trả lời được sau khi thấy output trên dữ liệu thật.

⇒ Ghi nhận để phiên sau **không** mở lại thảo luận kiến trúc trừ khi có output của T-1.1.1 và T-1.1.2.

## 6. Không thuộc phạm vi

- Giao tiếp REST giữa service — hệ mẫu **không** dùng; thêm khi có hệ thật dùng.
- Runtime discovery — O-1 là derived; persist + runtime là objective sau, có điều kiện.
- Topology của hệ không dùng message bus — R1–R3 vô nghĩa ở đó.
