## 1. Hai hình dạng hierarchy — và **một ràng buộc quyết định**

Operator mô tả đúng: `Epic → Story → Subtasks` **và** `Epic → Task → Subtasks`. Baplatform dùng **cả hai**, nhưng:

> **Ràng buộc đo được:** BAP là Jira **team-managed** ⇒ **`Story → Task` là KHÔNG THỂ**.
> (Jira team-managed chỉ cho 2 tầng dưới Epic.)

Nên họ đặt tên hai pattern:

| Pattern | Hình dạng | Khi nào | Ràng buộc |
|---|---|---|---|
| **A — mặc định** | `Epic → Story → Subtask` | việc TDD theo vai nằm **dưới Story** | `parent = Story` |
| **E — ngoại lệ** | `Epic → Task → Subtask` | chỉ khi capability **được >1 Story dùng** | phải **biện minh trong body** |

**Áp cho ESO:** project `ESO` đo được cũng là **team-managed (next-gen)** ⇒ **cùng ràng buộc**. Ta **không** có lựa chọn
`Story → Task`; mặc định là **Pattern A**.

## 2. Từ Story ra 4 subtask — **TDD quartet**

Đúng như operator nói: prompt từ Story ⇒ sinh ra nhiều subtask. Cụ thể là **bốn**, mỗi cái **một nhãn vai**:

| Ticket | Nhãn | Summary | SP mặc định |
|---|---|---|---|
| Unit tests | `tdd-unit` | `[be] … (unit tests)` | **2** |
| Implement | `tdd-impl` | `[…] Implement (DEV)` — **phải chứa chữ `Implement`** | **Σ WBS dev** |
| Coverage gate | `tdd-coverage` | `[…] (coverage gate)` | **1** |
| Scenarios + RTM | `tdd-qc` | `[qc] Scenarios + RTM` | **3** |

**Luật:** `tdd-impl` **chỉ** trên ticket Implement, **không bao giờ** trên một slice `TSK-*` đơn lẻ. Và **J-11**: tạo DEV
Task **đơn độc** (không UT/COV/QC, không link) là **cấm**.

## 3. Link nào ràng buộc cái nào — **lịch, không phải trang trí**

```text
Blocks (lane)   : UT → DEV → COV
                  DEV → QC
Blocks (theo vai): [be] UT → [be] Impl → [fe] Impl → [fe] E2E
                                     → [mo] Impl → [mo] E2E
                                     → [qc]
Relates (dấu vết): QC ↔ DEV · QC ↔ UT · QC ↔ COV
```

| Cấm tạo Blocks | Vì sao |
|---|---|
| UT → FE/MO/E2E/QC **khi đã có Impl** | Impl là mắt bắt buộc; UT không chặn kênh khác |
| QC → Impl hoặc E2E | QC **không** chặn việc implement |
| E2E → Impl hoặc QC | như trên |
| FE hoặc MO → QC | chỉ `[be] Impl` chặn `[qc]` |
| Impl → UT | ngược chiều |

**Ngữ nghĩa:** *"earlier **blocks**; later **is blocked by**"*. Nếu Impl của một kênh không có ⇒ `[be] Impl` chặn E2E của
kênh đó. Nếu không có ticket Impl ⇒ `[be] UT` chặn `[qc]`.

**Vì sao đáng học:** đây là **lịch thi công viết bằng link**, không phải bằng lời. Jira tự hiện "is blocked by" nên
**không ai phải nhớ thứ tự**.

## 4. SLP phân việc **dựa trên nhãn quartet** — đúng như operator mô tả

| Ticket | Peer nhận | Việc |
|---|---|---|
| `tdd-unit` | **dev peer** (`[be]`/`[fe]`) | viết unit/component test — **RED trước** |
| `tdd-impl` | **dev peer** | implement tới GREEN |
| `tdd-coverage` | **dev peer** | cổng coverage **≥80%** trên code chạm |
| `tdd-qc` | **QC peer** | scenario ↔ AC, execute, RTM |

Và **Lead** không viết code — Lead chạy `jira-impl.sh` lấy pack, gọi `plan-runtime` chia slice **rời nhau**, rồi spawn
peer theo slice. **"Ticket đầy đủ không"** là câu hỏi Lead trả lời bằng **DoR + Purpose & Clarity**, không bằng cảm nhận.

### 4.1 Định tuyến prompt → plane (agent tự route)

| Class | Tín hiệu | Plane |
|---|---|---|
| `delivery-intake` | "tạo Jira", "classify", "Ready", "enrich WBS" | **A** |
| `dev-runtime` | `BAP-…`, `Mxx.…Tnn`, "implement", "fix task" | **B** |
| `qc-runtime` | `tdd-qc`, "execute scenarios" | **B′** |
| `human-rework` | "QA fail", paste lỗi sau review | **B** |
| `docs-only` | chỉ sửa `sdlc/` | A (tier 2) |
| `question` | "giải thích" | — |

> **Nếu prompt lẫn lộn** (nói "implement" mà **không có** `task_id`) ⇒ agent phải **hỏi hoặc REWORK**, **không đoán AC**.

## 5. "Ticket đầy đủ" — Lead kiểm bằng **hai** thứ

### 5.1 Purpose & Clarity **P-01…P-07** (bắt buộc mọi ticket)

| id | Trục | Câu hỏi |
|---|---|---|
| P-01 | Purpose | Vì sao nó **tồn tại** — lý do nghiệp vụ/an ninh/tuân thủ |
| P-02 | Objective | Nó **làm gì** — hành vi, không phải tiêu đề |
| P-03 | Serves | Ai/ cái gì **tiêu thụ** nó |
| P-04 | Expects | Đầu vào nào, **cite** từng cái hoặc `OPEN:` |
| P-05 | Produces | Đầu ra cụ thể, **tách code ↔ tài liệu** |
| P-06 | Code vs docs | Phần nào là **code chạy**, phần nào **chỉ dấu vết** |
| P-07 | Risk if wrong | Sai thì **gãy gì**, mức nào, blast radius |

**Quy mô:** Story/US = đủ **P-01…P-07 + FIRST-READ**; Task = cả 7 trục, 1–2 dòng; Subtask = **P-01 + P-05 + P-06**.

> **FIRST-READ test (Story/US):** người **không có bối cảnh** phải hiểu vấn đề chỉ từ **Purpose + Objective + Serves** — không
> cần đọc AC/WBS/code. Chỉ hiểu sau khi đọc AC ⇒ **FAIL**, ticket **không Ready**.

### 5.2 Checklist DoR — ba nhóm

| Nhóm | Mục tiêu biểu |
|---|---|
| **Identity** | `task_id` SoT trong summary · **tiền tố vai** `[be]/[fe]/[mo]/[qc]` · label kebab `module-mxx`, `sot-1.9` · link SoT path · intake đã classify |
| **Scope quality** | có Purpose block · In/Out scope rõ · AC **Given/When/Then** · `OPEN` item được liệt kê · **không** bịa HTTP/DTO/Screen |
| **Delivery hooks** | parent + Depends/Blocks · Trace (US + WBS + Penpot) · **Task Sources** 6 mặt phẳng · Verification command · **SP** · TDD list |

Và **17 anti-pattern J-01…J-17**, đáng nhớ nhất:

| Mã | Cấm |
|---|---|
| J-01 | ticket **chỉ có tiêu đề** |
| J-02 | AC = "khớp Figma" |
| J-05 | tách Epic "Frontend" và "Backend" cho **cùng một capability** |
| J-11 | DEV Task **đơn độc**, không quartet, không link |
| J-14 | `tdd-*` trên Subtask mà parent **không phải Story** (Pattern A), hoặc trên Story/Epic |
| J-15 | Purpose block **rỗng hoặc nhắc lại tiêu đề** |
| J-16 | AC viết thành **bullet** thay vì bảng 8 cột |
| J-17 | bảng markdown **thiếu dòng** `| --- |` |

## 6. Trạng thái — ai được chuyển

| Chuyển | Ai | Điều kiện |
|---|---|---|
| → `needs-dor` / Backlog | **agent** | thiếu DoR; classify REWORK |
| → **Ready** | **agent**, chỉ khi VERIFIED + policy (hoặc PM exception) | template đủ + `class-verified` |
| → **In Progress** | **pod (người)** | kéo từ Ready |
| → **Human In Review** | **agent** sau verify PASS | comment + label + WBS `[HIL]` |
| → **Done** | **pod/TDM** | TDD DoD; không đóng `OPEN` im lặng |

**Một chỗ mâu thuẫn trong tài liệu của họ, ghi lại cho trung thực:** `delivery.workflow.mdc` §3 ghi `In Progress` = **pod**,
nhưng `delivery.jira-agent-execution.mdc` cho agent chuyển `In Progress` **khi bắt đầu** (và `jira-impl.sh --start` làm đúng
vậy). Cách đọc hợp lý: **agent được chuyển IP như một hành động khởi động**, còn **quyền sở hữu** trạng thái là của pod.

## 7. WBS atomic — 7 phần, 6 cột

Mỗi Task pack **phải** có theo thứ tự: header · **gap/issue inventory** (trước bảng) · pre-requisites · **bảng WBS** ·
dependency diagram · **Verification Task cuối** · related docs.

| Task Code | Subtask Code | Explicit Path File | SP | Status | Description |
|---|---|---|---:|---|---|

**Luật dòng:**
- dòng **Task** = header nhóm, **path rỗng**
- dòng **Subtask** = **đúng một** trong ba: (a) **một** đường dẫn file, (b) **một** lệnh verify/`cwd`, (c) `SKIP` kèm lý do
- **SP** bắt buộc trên dòng Subtask trước khi `Ready`; dòng Task = tổng con

> **Đây là "atomic" theo nghĩa thật:** một subtask = **một file** hoặc **một lệnh**. Không phải một khu vực.

## 9. Ba điều tôi hiểu sai trước khi đọc kỹ

| Tôi tưởng | Thực tế |
|---|---|
| "ticket đầy đủ" = có AC | **Purpose P-01…P-07 + FIRST-READ + DoR ba nhóm**; AC chỉ là một mục |
