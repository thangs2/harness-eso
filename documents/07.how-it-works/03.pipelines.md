# 03 — Pipelines: dữ liệu đi đâu, quyết định ở đâu

## 1. Preflight pipeline (collect → gate)

```mermaid
flowchart TB
  E["event: turn_start\n{userQueryStem, turnId}"] --> POL["resolveEsoPolicy(policy)"]
  POL --> DEC["decide(event, policy)\nL0 route + JEV facade"]
  DEC --> BUCKET["surface.bucket"]
  BUCKET --> SK["resolveSkillPack(surface)"]
  SK --> COL["runCollect"]

  COL --> LAW["lawAdapter.fetch(query)"]
  COL --> CODE["codeAdapter.fetch(query)"]
  COL --> MEM["memoryAdapter.fetch(query)\n(chỉ khi memoryFetch)"]
  LAW --> SCORE["scoreSufficiency\nlevel · score · gaps"]
  CODE --> SCORE
  MEM --> SCORE
  SCORE --> VER["buildTurnVerdict\nallowPromptSubmit · allowProtectedWrite · hardBlockers"]
  VER --> OUT["{facade, pack, retrieval, gaps, measure, verdict}"]
```

Module: `orchestrate-turn.mjs` → `collect.mjs` → `gate.mjs`. `hardBlockers` đến từ host (plugin chạy
`eso.checks` trước khi gọi verdict) — engine **không** tự đọc file mỗi turn.

## 2. Provider resolution pipeline

```mermaid
flowchart LR
  Q["kind: law|code|memory|verifier|reasoner"] --> CH["chain từ policy\n(prefer thay thế, không nối)"]
  CH --> N1{"provider kế tiếp\ntrong prefer"}
  N1 -->|"healthCheck fail"| N2["bỏ, thử tiếp"]
  N1 -->|"ok"| SEL["chọn"]
  N2 --> N3{"hết prefer?"}
  N3 -->|"còn fallback"| N4["thử fallback"]
  N3 -->|"không"| NONE["none"]
  SEL --> R["resolveWithReason"]
  N4 --> R
  NONE --> R
```

`ceiling` không phải điểm chặn: nó nói provider này **giỏi nhất tới đâu** (skills 0.5, session 0.65),
để quyết định có cần bind thêm nguồn chuẩn tắc hay không.

## 3. Check → blocker → quyết định

```mermaid
flowchart TB
  CFG["policy.eso.checks\n{contract, tenant, migration}"] --> L["loadCheckInputs(root, checks)"]
  L -->|"file không đọc được"| ERR["errors[]\n(không chặn hội thoại)"]
  L --> D1["diffContracts → breaking[]"]
  L --> D2["checkTenantFiles → findings[]"]
  L --> D3["checkMigrationFiles → findings[]"]
  D1 --> HB["hardBlockersFromChecks"]
  D2 --> HB
  D3 --> HB
  HB --> B["blockers[]\n{source, kind, ref, detail}"]
  B -->|"rỗng"| PASS["đi tiếp"]
  B -->|"có"| REC["appendBlockerRecord\n(product state)"]
  REC -->|"ghi lỗi"| LOG["log + VẪN chặn"]
  REC --> REJ["{kind:'reject'} / allowProtectedWrite=false"]
```

Marker là **quyết định của người**, không phải finding: `/* tenant:global */`, `/* breaking:approved */`
loại statement khỏi kết quả ở tầng check, không phải ở tầng gate.

## 4. Tool gate pipeline (write + shell, một đường)

```mermaid
flowchart TB
  TC["exec {name, arguments, agent}"] --> T{"tool"}
  T -->|"write/edit/…"| P1["path từ arguments"]
  T -->|"bash/pwsh"| C1["shellWriteTargets(command)"]
  C1 --> C2{"target resolve được?"}
  C2 -->|"không, có redirect"| UNRES["deny: write không có địa chỉ"]
  C2 -->|"không, không redirect"| LIT["quét literal tương đối\n(heredoc)"]
  C2 -->|"có"| ROOT
  P1 --> ROOT["root: config → session dir → target tuyệt đối → cwd"]
  LIT --> ROOT
  ROOT -->|"không phải consumer"| NOOP["không ý kiến"]
  ROOT --> MODE["pathMode(target, resolvePathPolicy, root)"]
  MODE --> LOCK{"locked?"}
  LOCK --> DENY["deny"]
  MODE --> ASK2{"ask / gated?"}
  ASK2 --> CONS{"consent còn hạn?"}
  CONS -->|"không"| APPR["approval(): deny hoặc ask theo askMode"]
  CONS -->|"có"| ALLOW["đi tiếp"]
  MODE --> FREE{"không tier?"}
  FREE --> ALLOW
```

Ba nguồn "target" theo thứ tự tin cậy: path tuyệt đối trong `arguments` → `shellWriteTargets` →
literal tương đối trong heredoc. `session dir` (service `workingDirectory`) là thứ khiến đường dẫn
tương đối gác được.

## 5. Verifier pipeline (M4)

```mermaid
flowchart LR
  CL["claim: route|guard"] --> MODE{"eso.verifier.modes[claim]"}
  MODE -->|"off"| HOST["verdict của host"]
  MODE -->|"shadow"| SH["host verdict + shadowDiff\n{host, verifier, agree}"]
  MODE -->|"active"| ACT{"provider khả dụng?"}
  ACT -->|"không + onUnavailable:fallback"| HOST
  ACT -->|"không + deny"| DENYV["deny"]
  ACT -->|"có"| PAID{"budget còn?"}
  PAID -->|"không"| HOST
  PAID -->|"có"| VV["verdict của verifier"]
```

Verifier **không bao giờ tự bịa verdict**: thiếu provider thì fallback host hoặc deny theo policy.

Đường phân biệt: **bằng chứng** (session, có thể bị agent sửa — chỉ để replay/đọc) vs **record**
(product state, gate tin). Một quyết định không bao giờ đọc record từ session.

## 8. Đường đi của một lần "deny"

```mermaid
sequenceDiagram
  participant M as Model
  participant H as Host
  participant G as Gate
  participant T as Trail
  participant U as Operator
  M->>H: tool call (write secrets/x)
  H->>G: pre-execute
  G->>G: pathMode → locked
  G->>T: append {kind: tool-deny, tool, ref, detail}
  alt ghi trail lỗi
    T-->>G: ok:false
    G->>G: vẫn deny (log lỗi)
  end
  G-->>H: {kind:'deny', reason}
  H-->>M: lý do model đọc được
  U->>T: đọc trail sau phiên
```

Đây là lý do tồn tại của `~/.harness/eso-blockers.jsonl`: host không ghi lại việc nó chặn, nên nếu ESO
không ghi thì không ai trả lời được "vì sao lệnh đó bị chặn".
