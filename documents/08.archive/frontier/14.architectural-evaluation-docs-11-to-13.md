## 2. Đánh Giá Chuyên Sâu Tài Liệu 11 (Synthesis & Co-Evolution)

### 2.1 Đóng góp nổi bật
1. **Phát hiện "Lỗ hổng vỡ cú pháp do Regex":** Nhận định chính xác việc dùng Regex đệ quy nông `\{[^{}]*\}` trong `codegraph-code.mjs` sẽ phá hủy mã nguồn C#/TypeScript (do string interpolation `$"..."`, regex literals, generics `<T>`, comments). Đề xuất chuyển sang Tokenizer/AST State-Machine 1-pass là quyết định sống còn.
2. **Hóa giải "Bẫy Đủ Ảo Tưởng" (Blind Sufficiency Trap):** Chỉ ra rằng việc Preflight hoàn toàn im lặng (`additional_context = undefined`) khi `SUFFICIENT` sẽ khiến Brain mất phương hướng khi user mở rộng yêu cầu ở turn sau. Sáng kiến **JIT-Pinning** (ghim 1–2 dòng mã `INV-*` đã xác thực, $\le 30$ tokens) cân bằng tuyệt vời giữa tiết kiệm token và neo giữ nhận thức.
3. **Mô hình Co-evolution hai chiều Upstream $\Longleftrightarrow$ Consumer:**
   - **SDLC 2 tầng:** Machine Spec (Invariants, Alerts) ở trên cho máy đọc; Human Context ở dưới cho người đọc.
   - **Jira "Delta-over-Anchor":** Thay vì chép toàn bộ spec vào Jira, chỉ gửi: *Anchor Link + Target Invariants + Delta Given-When-Then*. Giảm dung lượng ticket từ ~3.000 tokens xuống còn ~150 tokens.

### 2.2 Giới hạn còn tồn tại trong Doc 11
* **Hiện tượng Stale Pinning:** Chưa có cơ chế xác định xem Invariant đang ghim có còn khớp với prompt mới hay không nếu user thay đổi chủ đề trong cùng session.
* **Kỳ vọng Consumer bằng "Văn hóa":** Mô hình Delta-over-Anchor hoàn toàn dựa trên tính tự giác của con người (TPM/Dev). Thiếu chốt chặn kiểm tra tự động bằng máy.

## 3. Đánh Giá Chuyên Sâu Tài Liệu 12 (Debate Beyond Synthesis)

### 3.1 Đóng góp mang tính đột phá
Doc 12 nâng tầm hệ thống lên tiêu chuẩn của **Một Hệ Thống Phân Tán Bất Đối Xứng (Asymmetric Distributed State System)**:

1. **Đập tan "Ảo tưởng Tối ưu Token về 0":**
   - Chỉ ra rằng tối ưu 0 token trên từng turn là KPI sai lầm. 0 token mà khiến Brain thiếu dữ liệu, phải chat lại 5 lần (rewrite loops) thì tổng chi phí token thực tế cao gấp nhiều lần.
   - Xác lập lại hệ chỉ số KPI chuẩn: **Tokens per Successful Task**, **False-Sufficient Rate**, và **Stale-Continuation Catch Rate**.
2. **Task Fingerprint Invalidation ($F$):**
   - Định nghĩa hàm băm định danh tác vụ: $F = \text{SHA256}(\text{stem}, \text{rev}, \text{dirty}, \text{contract})$.
   - Ngăn chặn triệt để việc tái sử dụng verdict `sufficient` cũ khi người dùng đã đổi prompt hoặc sửa file trên working tree.
3. **Máy Trạng Thái Nhận Thức 4 Pha (Cognitive State Machine):**
   - Thay thế cờ nhị phân ngây thơ (`Sufficient` vs `Insufficient`) bằng 4 pha nhận thức:
     - **`COLD`**: Task mới hoặc chưa có bằng chứng $\rightarrow$ Eager mini-digest hoặc Gap playbook.
     - **`WARM`**: Vừa đạt đủ bằng chứng ở turn hiện tại $\rightarrow$ Ghim JIT-Pin ($\le 30$ tokens).
     - **`HOT`**: Receipt hợp lệ + $F$ khớp hoàn toàn $\rightarrow$ 0 token (Pull-only).
     - **`STALE`**: Fingerprint lệch do đổi prompt/sửa file $\rightarrow$ Buộc đo lại, cấm dùng pin cũ.
4. **Sufficiency $\neq$ Compliance:**
   - Khẳng định rõ: Việc gom đủ tài liệu chỉ chứng minh Agent *đã đọc*, không đảm bảo code sinh ra *tuân thủ*. Do đó, Write Gate (`guard-write.py`) bắt buộc phải độc lập và luôn fail-closed.
5. **Protocol-First thay vì Adapter-First:**
   - Khẳng định skeletonization là năng lực của công cụ `codegraph` (`viewMode=skeleton`), adapter chỉ là nơi truyền tải và fallback, tránh nợ kỹ thuật 2 tầng.

### 3.2 Lưu ý thực chiến đối với Doc 12
* **Mức độ phức tạp của HMAC Receipt:** Cần cân nhắc chi phí vận hành việc xoay secret key per-project. Trong môi trường local IDE, phân quyền thư mục Product State (`~/.harness/attestation/`) vốn đã đủ để ngăn chặn việc Agent can thiệp bất hợp pháp.

## 6. Ba Cảnh Báo Kỹ Thuật Khi Thực Thi Master WBS (Execution Watch-Outs)

Khi triển khai code thực tế theo Master WBS 13, bắt buộc phải tuân thủ 3 nguyên tắc sau:

### 6.1 Tối ưu hóa I/O cho Task Fingerprint (WBS-1.1)
* **Nguy cơ:** Việc gọi `git status --porcelain` trước mỗi prompt submit có thể gây độ trễ từ 100ms – 500ms trên các workspace lớn.
* **Yêu cầu kỹ thuật:** Chỉ kiểm tra dirty trên các thư mục mã nguồn cốt lõi (bỏ qua `node_modules/`, `bin/`, `obj/`, `.harness/cache/`). Sử dụng bộ nhớ đệm (debounce ~1.5 giây) để không gọi Git lặp lại liên tục trong các thao tác gõ nhanh.

### 6.2 Bảo đảm tính Tương Thích Ngược (Backward Compatibility - WBS-1.3)
* **Nguy cơ:** Thêm các trường `cognitiveState` và `pinnedInvariants` vào file `.eso-preflight.json` có thể làm gãy các test suite hiện tại (`qc/host-guards.test.mjs`, `qc/v1-preflight.test.mjs`).
* **Yêu cầu kỹ thuật:** Giữ nguyên 100% các trường cũ (`ok`, `level`, `score`, `allowWrite`, `gaps`), chỉ append thêm các trường mới.

### 6.3 Kỷ luật "Upstream First, Consumer Later"
* **Nguy cơ:** Vội vã đồng bộ Phase 4 sang `baplatform` khi Phase 1, 2, 3, 5 trên `harness-eso` chưa hoàn tất.
* **Yêu cầu kỹ thuật:** Toàn bộ test suite của `harness-eso` (`bun test`) phải xanh 100% trước khi tiến hành provision và cập nhật sang `baplatform`.
