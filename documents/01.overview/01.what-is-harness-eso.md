# What harness-eso is

## The problem it exists to solve

An AI coding agent in an IDE will happily write code it does not understand, in a repository whose
rules it has not read, and it will report success. Three things go wrong:

1. **It acts without evidence.** It edits a governed file after reading two files that do not contain
   the rule it is violating. Nothing stops it.
2. **Its work is not attributable.** A turn makes thirty tool calls; afterwards nobody can say which
   files it touched, which rules were in force, or what it cost. The IDE's own logs answer none of
   that.
3. **Nothing is verifiable.** "The agent said it ran the tests" is not a fact. There is no record of
   whether a verify command actually ran, or what it printed.

The product is a **control and observation layer** bolted onto an agent that was not built for any of
it. It works by hooking the IDE's own lifecycle events — the hooks the IDE already fires before a
prompt is submitted, before a shell command runs, after a file is edited — and turning those into
gates, records and a monitor.

## What it actually is, concretely

A monorepo of `@mu/harness-*` packages, plus a **host pack** that gets installed into a consumer
repo. After installation the consumer has:

- **Hooks** wired into its IDE(s), each a one-line invocation of the bundled pack.
- **Guards** that can deny a tool call: a write gate and a shell gate, owned by the consumer's repo.
- **A policy file** — `.harness/decision-policy.json` — that says which paths are protected, how the
  evidence gate behaves, and which optional subsystems are on.
- **An observe plane** — a server that ingests the hooks' trace and the agent's transcripts into
  SQLite, and serves a read-only web monitor.

And the machine has product state under `~/.harness/` — the project registry, one database per
project, and the records the gates trust.

## The three things it does

### 1. It gates

Before a protected path is written, or a shell command runs, a guard decides. The decision can come
from:

- **Static rules** — locked paths, secret files, protected path tiers.
- **Evidence sufficiency** — has the agent collected enough context (law it has read, code it has
  inspected) to act on this class of task?
- **A Brain call** — has the agent delegated the reasoning step to the configured model?
- **Human consent** — for paths a human reserved.

A guard that cannot decide **denies**. That is deliberate and is the single most important posture in
the system: an enforcement layer that silently stops enforcing is worse than no enforcement layer,
because the operator believes they are protected.

### 2. It attributes

Every tool call, file read, file edit, hook prompt and stop payload is ingested into a per-project
database, and attributed to a **request** — one user prompt and everything the agent did in response.
That is what makes the monitor able to answer "what did this turn do" rather than "what does this repo
look like".

Attribution is harder than it sounds and is where most of this project's defects have come from: the
IDE emits hooks as calls happen, while the transcript that defines turn boundaries arrives on a poll.
See `02.runtime/04.ingest-pipeline.md`.

### 3. It observes

A read-only SPA plus a REST/SSE API, showing per-request detail: the calls made, the tools used, the
token cost, the conformance checks, and graphs of which rules and decisions were in force.

## What it is *not*

Worth stating, because the boundary matters:

- **Not an agent.** It does not write code. It constrains and records an agent that does.
- **Not a sandbox.** It gates specific operations the IDE routes through hooks. It does not confine a
  process. An agent with unrestricted shell access has, historically, escaped these gates entirely —
  see the shell-write defects in `docs/04`.
- **Not a security boundary against a hostile agent.** Guards read files an agent could in principle
  write. The design goal is that the *honest path does not require the agent to grant itself
  permission*, plus attribution when it does — see `02.runtime/03.consent-and-attestations.md` for
  what is claimed and what is not.
- **Not the source of truth for a consumer's project rules.** The consumer owns those. The product
  reads them.

## Vocabulary in one table

| Term | Means |
|---|---|
| **consumer** | a repo the product is installed into; it has `harness.config.json` and `.harness/` |
| **turn** / **request** | one user prompt and the agent work it caused; id `<conversationId>:<n>` |
| **generation** | the IDE's id for one prompt; the only identifier that ties hooks to a turn |
| **ESO** | Evidence Sufficiency Orchestrator — the collect → score → gate subsystem |
| **gate** | a guard's decision: allow, deny, or (aspirationally) ask a human |
| **host pack** | the bundled, dependency-free script the IDE hooks invoke |
| **Brain** | the reasoning model the agent delegates a step to, via an MCP server |
| **Jev** | System One, an optional HTTP decision resolver for ambiguous choices |
| **dispatcher** | the agent model driving the turn (as opposed to the Brain it delegates to) |
| **observe plane** | the ingest server + monitor SPA (`:8792`) |
| **Console** | the project-management UI + API (`:8791`) |
| **attestation** | a record a gate trusts about a decision it did not make itself |

Fuller definitions with the file that implements each: [`02.concepts-and-glossary.md`](./02.concepts-and-glossary.md).
