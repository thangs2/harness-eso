# Concepts and glossary

Every term below is used precisely in the rest of this pack. Where a concept has an implementation
home, the file is named — that file is the authority, this is the orientation.

## Deployment shapes

### consumer

A repository the product is **installed into**. Distinguished by containing `harness.config.json`.
The dev consumer used throughout this project is **`x79`**; treat it as one example, not as a
requirement.

Where the text says `<consumer>`, read "the consumer's repo root".

A consumer has:

```
<consumer>/harness.config.json        # the anchor: project id, tenancy, storage
<consumer>/.harness/                  # consumer-owned runtime state (see 03.state-and-contracts/01)
<consumer>/.cursor/session/           # Cursor hook session dir
<consumer>/.agents/session/           # Antigravity hook session dir
```

A consumer is **not** allowed to live inside the `harness-eso` checkout. `buildProvisionPlan` refuses
that, because provisioning the product repo would write agent hooks into the repo that ships them.

### product state

Machine-wide state the product owns: **`~/.harness/`**. Contains the project registry, one SQLite
database per project, and the records gates trust (consent, attestations).

It is deliberately **outside every consumer repo**. Earlier versions kept it inside the checkout,
which made `git clean` destroy the project registry.

Implementation: `packages/harness-foundation/src/workspace-store.mjs`.

### observe plane

The ingest server and monitor: `packages/harness-observe-server` + `packages/harness-observatory`.
Serves REST, SSE and the built SPA on **`:8792`**.

### Console

Project management — add/remove projects, provision, reload host config, manage consent:
`packages/harness-console-server` + `packages/harness-console`, on **`:8791`**.

The split matters: Console **writes**, Observatory **reads**. A monitor that can mutate what it
displays is a monitor whose display you cannot trust.

## The turn model

### request / turn

One user prompt and all the agent work it caused. Primary key `<conversationId>:<boundaryIndex>`,
e.g. `0414718b-…:2`.

A request is created from the **transcript**, at a line containing `<user_query>`. Everything else in
the pipeline exists to attach evidence to one of these.

### conversation

One transcript file. One conversation contains many requests; requests are numbered from 1 in order of
appearance.

### generation

The **IDE's** identifier for one prompt, e.g. `70dea39c-97d0-49bb-8c22-222222222222`. A bare UUID.

This is the only identifier that ties a hook event to a turn: a tool call happening at 17:27 does not
announce which prompt caused it, but it does carry the generation. Getting this linkage right is the
single largest source of defects in this project — see `02.runtime/04.ingest-pipeline.md` and `F49`.

Beware a historical trap: `request.generation_id` may hold a **placeholder** equal to the request's
own id when no real generation was ever captured. `hasRealGenerationLink()` in
`packages/harness-observe-server/src/ag-request-enrich.mjs` is the only correct way to ask "is this a
real link".

### boundary index

The ordinal of a request within its conversation, starting at 1. Part of the request id.

## The ESO subsystem

### ESO

**Evidence Sufficiency Orchestrator.** Collect → score → gate. Answering: *does the agent have enough
context to be allowed to act on this class of task?*

- **Collect** gathers evidence: law (docgraph), code (codegraph), memory.
- **Score** produces `0…1` and a level: `insufficient` (< `T_low`), `partial`, `sufficient`
  (≥ `T_high` **and** no gaps).
- **Gate** turns that into a write decision, per policy.

Implementation: `packages/harness-eso-core/src/{collect,gate,orchestrate-turn}.mjs`.

### gap

A specific missing piece of evidence — `{kind, query, priority}`. Kinds seen in practice: `law`,
`code`, `symbol`, `doc`, `memory`, `check`, `human`.

A gap is actionable: each one maps to a suggested tool call in the UI's recovery playbook. Because
gaps and the score must agree about what a pack requires, they read the same field (see `F44` in
`docs/04`).

### pack

The evidence requirement for a **class** of prompt. Declares `minReadPaths`, `requiredDocTerms`,
`codeQueries`, and a bucket. Packs are selected by classifying the prompt: `tools`, `backend`,
`frontend`, `docs`, `general`, `root`.

Implementation: `packages/harness-eso-core/src/skill-pack.mjs`.

### preflight

The ESO run that happens **before** the agent starts work, triggered by the IDE's
`beforeSubmitPrompt`. It writes a verdict, injects an evidence block into the turn's context, and
records an attestation the write gate later reads.

Implementation: `packages/harness-host-generic/src/preflight-hook.mjs`.

## The decision subsystem

### L0 … L3

The decision **progressive-expansion** ladder. L0 is deterministic rule resolution; higher levels
escalate to more expensive resolvers. A decision records which level produced the winner
(`resolver_winner`) and whether it was ambiguous.

### Jev / System One

An optional **HTTP** decision resolver (`api.typesafe.ai`) used when L0 cannot resolve. It is **not**
an MCP tool and **not** an LLM call from the harness — it is a facade the harness calls directly.
`packages/harness-system-one`.

Consequence worth remembering: Jev calls are **not** MCP calls, and `decision_ledger` holds both Jev
and ESO rows, which is why counting them needs care (`F38` in `docs/04`).

### guard

A hook that can **deny** a tool call. Classified by `es.cognition.enforceBrain` and the consumer's
`decision-policy.json`. Two exist, and both are **consumer-owned** (Python, in
`<consumer>/.cursor/hooks/`):

| guard | fires on | protects |
|---|---|---|
| `guard-write.py` | `preToolUse` for Write/StrReplace/Delete | path tiers, secrets, evidence, Brain |
| `guard-shell.py` | `beforeShellExecution` | dangerous shells, and protected paths written via shell |

The pack deliberately ships **no** write gate. `dispatch.mjs` documents why at length: a pack copy
checked evidence but not paths, so with enough evidence it allowed edits to the consumer's most
protected files while blocking ordinary `src/` edits. The consumer owns this, and the product does
not duplicate it.

## The model tier

### Brain

The reasoning model the agent **delegates** to. Reached over MCP (`deepseek-direct`), not called
directly. Three tiers exist and they are **not** interchangeable:

| tier | how | meaning |
|---|---|---|
| **Pro** | `ask_deepseek_pro` | deepest reasoning, thinking on |
| **Brain Flash** | `ask_deepseek_flash` with prompt prefix `[BRAIN FLASH]` | fast reasoning, thinking on |
| **Brain Fallback** | `ask_deepseek_flash` with `[BRAIN FALLBACK]` | Brain role when Pro is down |
| *executor* | `ask_deepseek_flash`, no prefix | **thinking off** — tooling, not reasoning |

The tier is decided by a **prompt prefix**, not by the tool name. This is why the observer cannot
classify by tool name alone (`F31` in `docs/04`), and why an executor call must not count as Brain
work.

### dispatcher

The agent model driving the turn (in this project, Cursor's own Composer). Distinct from the Brain it
delegates to. Tokens the IDE's `stop` hook reports are the **dispatcher's**, not the Brain's — the
single most misleading fact in the token story (`F32`).

### MCP

Model Context Protocol. The transport for both model tools (`ask_deepseek_*`) and ordinary tools
(Jira, memory, browser). **Model calls and tool calls share this transport and nothing else** — they
have different costs and different counts (`F37`).

## Records a gate trusts

### attestation

A record a guard reads to learn a fact it did not compute itself. Two exist, both under product state:

| attestation | writer | answers |
|---|---|---|
| `<state>/attest/<projectId>.json` | the pack's preflight hook | how sufficient was the evidence |
| `<state>/deepseek-usage.jsonl` | the DeepSeek MCP server | did a Brain-tier call complete |

They exist because the alternative — a stamp in the consumer's session dir — is a file the **gated
party can write**. See `02.runtime/03.consent-and-attestations.md`.

### consent

A human approval for a path reserved with the `ask` tier. `<state>/consent/<projectId>.json`, written
**only** by the Console API. An agent cannot grant it, by construction.

### path tier

Four modes, resolved from the consumer's `decision-policy.json` `paths` key:

| tier | meaning | openable by |
|---|---|---|
| `locked` | reserved for humans | nobody — not by evidence, not by consent |
| `gated` | needs evidence **and** a Brain call | satisfying both |
| `ask` | a human must approve | consent only |
| `sot` | **label only** — a source-of-truth registry | n/a — it never denies |

`sot` is deliberately not an enforcement tier. Source-of-truth and protected are **independent axes**:
`<consumer>/sdlc/08.wbs/` is a source of truth the agent must maintain, while `<consumer>/scripts/ci/`
is not a source of truth and is protected anyway — see `F46`.

## The host pack

### host pack

A **bundled, dependency-free** script plus helper, installed into `<consumer>/.harness/host-pack/`:

| file | role |
|---|---|
| `harness-hook.mjs` | the dispatcher — every hook implementation, zero imports outside `node:*` |
| `route-hook.py` | trace writer (also handles the Antigravity dialect) |
| `path-policy.default.json` | generated default path policy, for the Python guards |
| `host-pack.json` | version + per-file sha256, so a partial install is detectable |

Why bundled: the first design shipped one script per hook plus a shim that spawned the implementation
out of the product checkout, which made the checkout a runtime dependency of the consumer. `git clean`
in the product repo broke consumer guards.

### dispatcher

`harness-hook.mjs`. Invoked as
`node .harness/host-pack/harness-hook.mjs --hook <name> --tree <cursor|agents>`. `--tree` selects the
session directory and the response dialect; hook code is IDE-agnostic.

Hook ids: `guard-shell`, `guard-brain`, `preflight`, `route`, `gap-tracker`, `post-tool-hint`,
`pre-compact`, `shell-targets`.

`shell-targets` is the odd one: it is **not** wired to any IDE event. It is a **query** the consumer's
`guard-shell.py` runs to learn which files a shell command writes, and it prints JSON rather than a
permission payload. Wiring it to an event would replace a real guard's decision with that JSON.

### hook dialect / shape

Two response dialects, selected by tree:

- **Cursor** — flat `{hooks: {<event>: [...]}}`; hooks return `{permission: "allow"|"deny"}`.
- **Antigravity** — named blocks `{<block>: {<Event>: [{matcher, hooks: [{type, command}]}]}}`; hooks
  return `{decision: "allow"|"deny"}`.

`detect_shape()` picks by payload, not by tree, so a payload from either IDE is handled correctly
(`packages/harness-host-generic/src/hook-io.mjs`).

**There is no `ask`.** Cursor's hook contract accepts only `allow` and `deny` — verified from the
shipped bundle, which warns `'ask' permission … is not yet implemented. Use 'allow' or 'deny'`. A
hook therefore cannot prompt a human; the `ask` tier is enforced with a message naming what the human
must do, pending a consent channel that is not a hook.

## Posture and failure

### fail-closed

A guard that cannot decide **denies**. The default for guards, and overridable per consumer by
`guards.unavailable: "deny" | "warn"` in the decision policy.

A telemetry hook (trace, hint) fails **open** instead: breaking a developer's turn because a trace
line could not be written would be a worse bug than the missing line.

### enforcement posture

`eso.enforceWrites` — `"fail_closed"` (enforce the evidence gate) or `"off"` (disable it). It is **not**
a three-value setting: `"observe"` reads like a valid value (it *is* a valid `eso.mode`) but was never
one here, and silently coercing it to the strictest posture was `F24`.
