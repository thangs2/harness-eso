# Knowledge base — what this product is, and what we decided it is

**Read this after `00.README.md`, before `05.development/02.invariants.md`.** That file lists the rules
whose violation already caused a defect; this one states the *product* those rules protect, in the four
terms a person needs before they can disagree with it: **concept**, **mission**, **vision**, **feature**.
Every claim here cites where it is enforced in code, because a document that states intent the code does
not have is the defect class this repo is built to avoid (G-16).

> **Why this file exists.** Atrievefin, 2026-10-23, the operator — who has read this repo for weeks —
> wrote: *"tao thực sự càng ngày càng cảm giác mất hiểu biết"*. Nothing was broken. The product had grown
> a boundary (`harness-eso` provisions · consumer configures) that was **true in code, decided in
> comments, and written nowhere an operator would look**. The fix is not more prose in the README: it is a
> single page that says what the thing is, who owns which half, and how to check both from state.

---

## 1. Concept — what it is

**Harness ESO** (*Evidence Sufficiency Orchestrator*) is the set of guards, telemetry and monitoring that
run **around** an AI coding agent in an IDE, so that the agent's work is:

| Property | Means | Enforced at |
|---|---|---|
| **gated on evidence** | a write to a protected path needs evidence that supports it; a turn that cannot gather it is stopped rather than trusted | L3 `buildTurnVerdict`, L4 `guard-write.py` |
| **attributed to a turn** | every decision belongs to one request/generation, not to "the agent" in general | L_ingest `ingest-transcript.mjs` |
| **observable** | what happened is a query, not a memory | Observe REST + Observatory |

Three properties, and each one is a *plane* concern — which is why the architecture splits in two:

- **Control plane** — decides *this turn*, inside the IDE, synchronously, and **must be able to decide
  alone**. If it needed the observer, every prompt would fail when the observer is down.
- **Observe plane** — records and attributes, in a separate process, read-only over the consumer's tree.

**It is not a framework for building agents.** It does not call the model, own the prompt, or replace the
IDE. It is the layer that sits between the agent and the repo, and it is installed *into* a repo
(a **consumer**) that already lives without it.

Two words carry the whole configuration model, and conflating them is the confusion this page resolves:

| Word | Owns | Examples |
|---|---|---|
| **mechanism** | how a decision is made at all | the guard, the sidecar, the policy **schema**, the default adapter selection, the gate math |
| **value** | what the decision is made **with** | which paths are `locked`, what this project's SoT is, the real Brain tier, whether Jev/L3 are on, the `SDLC/` tree |

`harness-eso` ships mechanisms. The consumer owns values. **§4** is the per-key form of that sentence,
and it is enforced by a test, not by this paragraph.

## 2. Mission — what it does, every day

> **Make "the agent said it was fine" a checkable claim, on the turn it happens.**

Concretely, on a single turn, the product does four things and refuses to skip any of them:

1. **Route** the prompt to a pack (`L0`) — so "required evidence" means something specific to this kind
   of work, not a generic checklist.
2. **Collect** law / code / memory evidence and name what is **missing** (`L1`) — a gap with a name, never
   "seems fine".
3. **Score** and **gate** (`L2`, `L3`) — `level` + `score` decide whether a protected write may proceed,
   and the verdict says *which* gap blocked it.
4. **Report** the decision where two humans can see it — the operator in the reply (`[ESO EVIDENCE GAP]`),
   the history in the Observatory.

**What it is deliberately not for:** making the agent smarter, writing the code, or acting as a model. The
brain tier (`L5`) is a *call the consumer must make first* when the evidence is insufficient — the product
only decides whether that call is required.

The mission has a shadow, and it is load-bearing: **a false "allow" is worse than a false "deny"**. Every
default in this repo follows from it — `create-if-missing` guards, `fail_closed` postures, deny messages
composed from the verdict. When a default looks paranoid, this sentence is the reason.

## 3. Vision — where it is going

> **The consumer's configuration becomes visible, editable and verified from one place — and the
> product never guesses a domain value.**

> **Scope note (2026-10-24).** This section is the *reference* view: what the vision commits the **code** to,
> and where that is enforced. The **direction** view — vision · mission · goals · objectives with falsifiable
> tests, the landscape, the roadmap and the decision log — now lives in
> [`09.sdlc/`](../09.sdlc/00.index.md). When the two disagree about *where we are going*, `09.sdlc/` owns it;
> this page owns *what the code currently guarantees*.

Three steps, in the order the repo is actually taking them:

| Step | State | Evidence in code |
|---|---|---|
| **1. The boundary is checkable from state** | **done 2026-10-23** | `harnessctl init report` (per key: product / overridden / consumer) · `harnessctl ownership explain` (intent + the document that declares it) · `policyOverwrites` in the `init profile` result |
| **2. The same boundary is a screen** | next | Console project page reads the same two commands; F-CS in the feature map |
| **3. ESO supplies the machinery to declare a domain** | later | a consumer can add a policy key, a path tier or a Brain adapter **through the product's own schema**, and `init report` classifies it without a code change |

What the vision explicitly rejects:

- **The Console will not become a second source of truth.** It renders `init report` and writes through
  the same merge (`deepMergePolicyObjects`). A UI that keeps its own policy document would re-open the
  exact split (`decision-policy.json` vs `workspace.json`) that `init-profile.mjs` already closed once.
- **The product will not ship domain values.** A default `paths.locked` list is a *seed*, labelled as
  such; the runbook names the consumer as the Source of Truth, and `ownership explain` prints both.
- **No auto-heal of consumer intent.** `sync-guards` replaces a *stale product file*; it never touches a
  `customised` one. Step 1 exists to make the difference visible, not to erase it (G-17).

## 4. The two sides, and the line between them

```
harness-eso   ──provision──▶  .harness/decision-policy.json  ◀──configure──  consumer
  mechanism                     the meeting point                   value
  (hooks, guards,               product seeds keys,                 (paths.locked, sot,
   sidecar, schema,             consumer owns values,               brain tier, SDLC/)
   default adapters)            merge never drops unknown keys
```

**The write contract is four modes, and each feature row is one of them** (`init-profile.mjs`,
`writePlanFiles`):

| Mode | Who wins | Example |
|---|---|---|
| `skip` | the existing file | consumer rules / skills already on disk |
| `create-if-missing` | the first writer | guards (so a consumer *may* customise — and then `guard-freshness` reports it) |
| **merge** | product wins per key, consumer keeps unknown keys | **`.harness/decision-policy.json`** |
| `update` | always product | `integrations.json`, `harness-hook.mjs` |

Merge is the only mode where a consumer decision can be replaced, which is why it is the only mode with a
report: before 2026-10-23 it printed `status: merged` whichever way the merge went.

**How to check, without reading code** — this is the operational form of §4:

```bash
harnessctl init report ../atrievefin            # what is, and what the next provision changes
harnessctl init report ../atrievefin --json     # { policy: {product, overridden, operator}, guards, verdict }
harnessctl ownership explain paths.locked       # who owns it BY DESIGN, and the document that says so
```

`init report` answers **what a provision does**; `ownership explain` answers **what the product means**.
They are allowed to disagree, and the standing case is `paths.locked`: the plan seeds a list, so report
calls it product-owned; the runbook calls that list the consumer's, so explain says `consumer`. A reader
who needs to settle it needs both, and both are one command.

## 5. Feature list — what can be turned on, and by whom

The complete table (30 features × plane / layer / **ownership** / enforcement / trigger / probe / lever /
maturity) lives in [`05.development/10.feature-and-classification-map.md`](../05.development/10.feature-and-classification-map.md)
§3 and is linted against the code. This is the map of that map — six groups, in the order a consumer meets
them:

| Group | Why a consumer cares | Features | Mostly owned by |
|---|---|---|---|
| **Provisioning & verify** | getting installed, and knowing which tier you reached | F-IP, F-HP, F-HM, F-VF | shared — the product chooses *how*, the consumer chooses *what* |
| **Evidence loop** | the reason the product exists: collect → name gaps → score | F-RT, F-PK, F-CL, F-GAP, F-UA, F-MISS, F-SC, F-PJ | product core; `shared` where a lever exists (`eso.sources`, thresholds) |
| **Write control** | why a write was refused, and whether a human can approve it | F-WG, F-EW, F-BR, F-GW, F-GS, F-DN, F-HL, F-PD | `shared` or `consumer` — every one reads a consumer value |
| **Host pack** | the same gates inside Cursor, Claude Code and Antigravity | F-AT, F-IR, F-DS | product mechanism (`shared` for context injection) |
| **Observe plane** | "what happened" as a query | F-IN, F-ES, F-API, F-OB | product; the *history* is the consumer's data |
| **Operator surface** | one place to see and drive the above | F-CS, F-DR, F-TD | `shared` (Console), product (doctor, token diet) |

**Choosing a lever** is the one thing that must never be guessed — §4.3 of the feature map records, per
lever, what it changes **and what it does not** (`eso.mode` does not change the evidence gate;
`paths.*` does not change the evidence level). If a lever is not in that table, it is not supported, and
the answer to "can I turn this off?" is "not that way".

## 6. Ground rules for changing this page

1. **Every claim here is either enforced in code or cites the file that enforces it.** If you change a
   claim, change the test in the same commit — `qc/feature-map.test.mjs` (ownership column, vocabulary) and
   `packages/harness-cli/src/ownership-claims.test.mjs` (every profile subtree has an owner, every citation
   exists).
2. **Adding a policy subtree to `profiles/generic-eso.json` without an ownership row fails the test.**
   Silence is how `paths.locked` came to have two owners.
3. **This page is not a runbook.** Steps live in `02.runtime/08.provisioning-consumers.md`; this page
   explains *why* those steps are shaped the way they are.
