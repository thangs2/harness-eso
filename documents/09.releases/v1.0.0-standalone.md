# harness-eso v1 — release note and close-out

**Branch:** `v1.0.0-standalone` (cut from `standalone-core-engine` at `3a68fb6`)
**Date:** 2026-10-27
**Status:** v1 is **closed for new features**. Development continues on v2 in a separate thread.

This file exists so the v2 thread does not have to reconstruct v1 from git history and guesses.
It states what v1 is, what it is **not**, and which of its behaviours are load-bearing — because
several of them look like defects until you know which failure they were chosen over.

---

## 1. What v1 is

A monorepo shipping `@mu/harness-*`: guards, evidence gating, telemetry and monitoring that run
**around** an AI coding agent in an IDE. See `00.README.md` for the product description; this file
does not repeat it.

## 2. Host support — the honest version

`00.README.md` claims *Triple-Host Parity* across Cursor, Antigravity and Claude Code. **That claim
is accurate for those three and was never extended to a fourth.** The state at v1 close:

| Host | Write gate | Evidence gate | Brain gate | Preflight |
|---|---|---|---|---|
| Cursor (`.cursor`) | ✅ | ✅ attestation | ✅ ledger → stamp | ✅ command hook |
| Antigravity (`.agents`) | ✅ | ✅ attestation | ✅ ledger → stamp | ✅ command hook |
| Claude Code (`.claude`) | ✅ | ✅ attestation | ✅ ledger → stamp | ✅ command hook |
| **DSH** | ✅ plugin | ✅ plugin | ✅ **plugin-witnessed** | ⚠️ check-only, weaker |

DSH is a **fourth host that does not have parity**. On it:

- The gate is a Cordis plugin (`packages/harness-eso-dsh`), not a command hook. DSH has no command
  hook mechanism.
- The evidence verdict is **check-only**: it says "the consumer's declared `eso.checks` produced no
  blocker". It is *not* a docgraph/codegraph sufficiency measurement, because those adapters are MCP
  servers bound to the other hosts' tool sets. The receipt records this in `source`.
- Brain evidence is **witnessed by the plugin** (`tools/post-execute`), not read from the DeepSeek
  usage ledger — see §4.2 for why that is not laziness.

Anything that assumes a fourth host behaves like the three will be wrong. Say "three hosts plus
DSH", never "four hosts".

## 4. Behaviours that look like bugs and are not

Read this section before "fixing" any of them.

### 4.1 The session directory is not always `<repo>/.<tree>/session`

`HARNESS_SESSION_DIR` overrides it with an absolute path, for a host whose sessions live outside the
repo (DSH: `~/.dsh/sessions`). An override that lands **inside** the repo is refused at import time,
not ignored — a session dir the agent can write is reachable as a gated path, and its exemption would
be forgeable.

`guard-write.py` derives the value from its own file path; the pack calls
`@mu/harness-foundation`'s `sessionDir`. These must agree, and a test asserts they do. They used to
be two independent copies, which is how the pack would have written a stamp the guard never read.

### 4.2 The DeepSeek ledger is **not** movable into a workspace

The Brain gate's primary evidence on the three IDE hosts is `~/.harness/deepseek-usage.jsonl`, written
by the MCP server. On DSH that child cannot write product state (sandbox), so an earlier analysis
recommended pointing `DEEPSEEK_USAGE_LEDGER` into the workspace.

**That recommendation is withdrawn.** A ledger the MCP child can write inside a workspace is a ledger
the agent can append to, which makes it forgeable evidence for the gate it is supposed to satisfy.
DSH instead has the plugin witness the call; the ledger route is untouched for the other three hosts.

If you are ever about to "fix" a missing Brain record by moving the ledger, re-read this paragraph.

### 4.3 `ask_deepseek_flash` is not Brain evidence

`BRAIN_TOOLS` in `brain-attestation.mjs` is `{ask_deepseek, ask_deepseek_pro}`. The flash tier exists
precisely so work can proceed *without* a Brain call; counting it makes the gate free to satisfy. An
earlier version counted it and a test caught it.

### 4.4 A receipt minted by the pack is never overwritten by the plugin

`receiptMatchesVerdict` returns `false` for any receipt whose `source` is not
`dsh-plugin-checks`. The pack's receipt carries a real measurement; replacing it with a check-only
verdict would weaken evidence the guard trusts.

### 4.5 `stampWrites: "exempt"` relaxes real protection

It is off by default. Turning it on means the agent may write `.pipeline-brain-stamp.json` without a
host approval prompt — and that stamp is what `brain_attested_legacy` believes. On a host that reads
the ledger first this costs nothing; on a host that relies on the stamp it is a genuine relaxation.
The key exists as a **declaration**, so a consumer that accepts the trade says so in its policy.

## 6. Where v2 starts

Not a roadmap — a record of what v1 deliberately left undone, so v2 does not rediscover it as new:

1. **Real sufficiency measurement on DSH.** The check-only verdict is honest but weaker. Either port
   the docgraph/codegraph adapters to that host's tool surface, or state permanently that DSH does
   not do `dev-runtime`.
2. **One session-dir rule, everywhere.** `guard-write.py` still derives its own default rather than
   reading a shared constant. Correct today, and a place for the two to drift.
3. **The overlay-row question.** `P3.patch-ids` is a warning today and could become a plugin that does
   not load. v2 should decide whether overlay rows are supported at all.
4. **Ledger freshness.** `check brain` reports it; nothing renews it. Consider whether a stale ledger
   should degrade to `ask` rather than `deny`.
