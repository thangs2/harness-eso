# harness-eso — documentation pack

**Read this file first.** It tells you what this project is, where to look for what, and which
statements in this repo are load-bearing.

## What this is

`harness-eso` is a **monorepo that ships a product**. The product is the *Harness Evidence
Sufficiency Orchestrator* (ESO): a set of guards, telemetry and monitoring that runs **around** an
AI coding agent in an IDE, so that the agent's work is gated on evidence, attributed to a turn, and
observable.

It is published as packages in the `@mu/harness-*` npm scope.

### Supported Hosts (Triple-Host Parity)

Harness ESO operates with 100% parity across three primary AI agent environments:
1. **Cursor (`--tree cursor`)**: Flat `hooks.json`, `.cursor/rules/*.mdc`, workspace project transcripts.
2. **Google Antigravity (`--tree agents`)**: Protobuf hook contract, nested `hooks.json`, CWD self-heal, bounded tool cache queue, `.agents/rules/*.md`, global brain transcript attribution.
3. **Claude Code (`--tree claude`)**: `hookSpecificOutput` envelope, `.claude/settings.json` 3-way merge, `CLAUDE.md` law gate, project JSONL transcript with token & cache read attribution.

## Who these documents are for

Written to be **read by another AI agent** that is picking this project up cold. That shapes the
style:

- Statements are either **verified** (with the command or file that shows it) or **marked as open**.
  There is no "should work".
- Design decisions carry the **reason** and the **defect** that produced them, because in this repo
  almost every non-obvious rule exists to prevent a specific failure that already happened.
- Failure modes are documented with the **diagnostic** that distinguishes them.

## Isolation

**These documents are self-contained.** Nothing here requires reading another repository.

- The sibling repo `x79` is an **example consumer** (a repo the product is installed into), and is
  referred to as `<consumer>` throughout. Where a concrete path helps, the dev consumer `x79` is
  named explicitly and labelled.
- Do **not** treat `x79/document/harness/**` as design law. It is the original specification and is
  **known to be out of date** relative to this code. This repo's code and these documents are the
  current truth.

## The two documentation roots

This repo deliberately has two, and they answer different questions:

| Root | Holds | Nature |
|---|---|---|
| `documents/` (**this pack**) | what the system **is** and **how it works** | stable, curated, the handover |
| `docs/` | the **live defect log** (`04.standalone-revamp-wbs.md`, ~2,500 lines) and operator runbooks | chronological, append-only, includes work in progress |

If the two disagree about behaviour, `documents/` is the description and `docs/` is the evidence.
`docs/04` is where every numbered defect (`F1` … `F50`) lives; this pack cites those numbers rather
than restating them.

## Ground rules for continuing this project

1. **`AGENTS.md` at the repo root is the supreme law of this repo.** It is short. Read it.
   `.cursor/rules/*` only routes you to it.
2. **`05.development/02.invariants.md` lists the rules whose violation has already caused a
   production defect here.** Read it before changing how data flows.
3. **Do not run the full ESO pipeline on `harness-eso` itself.** This repo *ships* the product; the
   pipeline runs on a **consumer**. Provisioning this repo would install hooks into the repo that
   builds them.
4. **Verify against a consumer.** Unit tests (`bun run test`) prove logic. Behaviour — what an agent
   actually experiences — is verified on a consumer with the product installed, because that is
   where hooks, guards and the observe plane meet.
