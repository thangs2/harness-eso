# CLI reference

Two entry points. They are not the same thing and are not interchangeable.

| | `./harness` | `harnessctl` |
|---|---|---|
| what | a thin shell wrapper for the common operator path | the real CLI |
| where | repo root, made executable by `install.sh` | `node packages/harness-cli/src/cli.mjs`, or `bun run harnessctl` |
| surface | `console`, `init profile`, `host-pack`, `up`, `down`, `restart`, `status`, `health`, `logs` | everything, including `observatory`, `configure`, `project` |

`./harness up` is what an operator runs. `harnessctl` is what to reach for when the wrapper does not
cover the case. The wrapper forwards to the same implementation, so behaviour cannot diverge.

## Operator scripts (the only sanctioned surface)

When driving a consumer — provisioning, deploying, verifying — go through these four and nothing
else. Agent rule: `.cursor/rules/core.entrypoints.mdc`.

| Script | Does | Exit codes |
|---|---|---|
| `./provision.sh <consumer\|all> [--plan] [--force] [--host-mode <m>]` | resolve the consumer, run `init profile`, print the host tier | 0 ok · 1 provision failed · 2 unknown consumer |
| `./deploy.sh <consumer\|all> [--plan] [--no-build] [--smoke]` | build SPA + image, restart `harness-observatory-<id>`, verify `/health` and `/api/tenant` | 0 deployed · 1 failure · 2 unknown consumer |
| `./verify-consumer.sh <consumer\|all> [--json] [--strict] [--out <dir>]` | T0–T5 maturity report; writes only `.harness/diagnostics/` | 0 clean · 1 CRITICAL/strict · 2 unknown consumer |
| `./console.sh [up\|restart\|down\|status\|health\|logs\|build\|verify\|smoke]` | the Console on `:8791`, one server for N profiles | 1 when `verify` fails |

`--plan` on `provision.sh` and `deploy.sh` writes nothing and starts nothing — it is the first step of
any case-by-case run, and safe to repeat. On Windows: `harness.ps1 <deploy|provision|verify|console>
<args…>`, which finds Git Bash (or WSL with `HARNESS_WSL=1`) and forwards argv unchanged.

## `./harness`

```bash
./harness console                     # Console on :8791, foreground
./harness init profile <path> [flags]  # provision a consumer (see below)
./harness host-pack <sub> <consumer>
./harness up | down | restart | status | health | logs
```

`up` builds the image and brings compose up, so the Observatory is on `:8792` when it returns.

## `harnessctl`

```
harnessctl init profile <consumer-path> [--plan] [--id <id>] [--name <name>]
                                       [--port <port>] [--host-mode dual-ide|superset]
                                       [--host-profile <id>] [--force]

harnessctl host-pack status|refresh|add-ide|remove-ide [consumer | --project <id>]

harnessctl verify consumer <path|--project <id>> [--json] [--strict] [--out <dir>]

harnessctl fix consumer <path|--project <id>> [--dry-run] [--from-latest] [--force-provision] [--no-provision] [--strict] [--json]

harnessctl configure list
harnessctl configure use <id>

harnessctl observatory up|down|restart|status|health|logs|build|smoke [--project <id>]
harnessctl console     up|down|restart|status|health|logs|build
```

### `init profile`

| Flag | Effect |
|---|---|
| `--plan` | **dry run** — print the plan, write nothing. Do this first, always. |
| `--id <id>` | project id; also the database directory name |
| `--name <name>` | display name |
| `--port <port>` | the project's observe port |
| `--host-mode` | `dual-ide` (Cursor + Antigravity) or `superset` |
| `--host-profile <id>` | pin one host profile instead of the mode's default |
| `--force` | rewrite `harness.config.json` from the plan — the **only** supported repair for a stale anchor |

Without `--force`, `harness.config.json` is **create-if-missing**, so a wrong value in it is permanent.
With `--force` it is rewritten and operator keys outside the plan are **dropped** — which is why it is
opt-in.

`decision-policy.json` is always merged, never force-written.

### `host-pack`

| Subcommand | Action |
|---|---|
| `status` | version, `integrity`, `verification`, hook counts per IDE tree |
| `refresh` | reinstall the pack and re-merge hooks — idempotent |
| `add-ide` / `remove-ide` | add or remove a tree's wiring |

Accepts either a consumer path or `--project <id>` (resolved through the registry).

`refresh` after any change to `profiles/` — hook wiring lives there. Then **reload the IDE window**.


### `verify consumer`

Read-only maturity diagnostic against `profiles/standards/consumer-maturity.v1.json`.

Writes `<consumer>/.harness/diagnostics/latest.{json,md}` (+ timestamped copies). Exit `1` on CRITICAL fail; `--strict` also fails on WARN.

See [`05.consumer-maturity-standard.md`](../03.state-and-contracts/05.consumer-maturity-standard.md).

### `fix consumer`

Semi-auto remediations from the maturity diagnostic. AUTO-SAFE only (sync WORKFLOW_GUIDE, session dirs, host-pack refresh, optional provision). Domain gaps → `OPEN_FIXES.md`.

See [`05.consumer-maturity-standard.md`](../03.state-and-contracts/05.consumer-maturity-standard.md) §7.

### `observatory` / `console`

| Subcommand | Action |
|---|---|
| `up` / `down` / `restart` | compose lifecycle |
| `status` / `health` / `logs` | inspect |
| `build` | rebuild the image (runs the host SPA build first) |
| `smoke` | health + ingest + requests sanity |

`observatory` needs a consumer: pass `--project <id>` or run
`./deploy.sh up <consumer-path>`.

### `configure`

| Subcommand | Action |
|---|---|
| `list` | configured projects |
| `use <id>` | set the default project |

`configure add` **was removed** — provisioning writes consumer files and must go through
`init profile`, which is idempotent and merges. The CLI prints a pointer rather than failing obscurely.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | success |
| `1` | the operation ran and failed |
| `2` | usage error, or a precondition the planner refuses (e.g. a consumer inside `harness-eso`) |

## Developer commands (in the checkout)

Not operator commands, but the ones you will use while working on the product:

| Command | Does |
|---|---|
| `bun install` | dependencies (Bun workspaces) |
| `bun run test` | **all** Bun test suites — `node scripts/run-tests.mjs` |
| `bun test` | only `qc/` (the root `bunfig.toml` pins it) |
| `bun run test:observatory` | Vitest, the SPA |
| `bun run test:all` | both |
| `bun run build:host-pack` | rebuild the pack (asserts zero external imports) |
| `bun run sync:diagrams` | verify the diagram compilation matches the Console's diagrams (`--write` to repair) |
| `bun run build:observatory` | rebuild the SPA — **required before the server or image serves it** |
| `bun run bench:ingest` | ingest benchmark |
| `bun run observe:server` | run the observe server from the checkout |
| `bun run dev:observe` | API + Vite with HMR, no Docker |

Two things about the test commands, both learned from a defect:

- **`bun test` alone does not run everything.** `bunfig.toml` pins `[test] root = "./qc"` so a bare
  `bun test` is the fast unit run — and that setting **overrides paths passed on the command line**.
  Listing five directories ran only `qc`, which is why `scripts/run-tests.mjs` exists: it runs each
  suite from inside its own directory. `bun test --root` is not a supported flag. (Eight test files in
  `harness-observe-server` had never executed because of this.)
- **`build:observatory` is a prerequisite, not a convenience** for anything that serves the UI. A
  stale `dist/` looks exactly like a fix that did not work.

## A worked sequence

```bash
# 1. product, once
./install.sh
./harness up

# 2. link a consumer — dry run first
harnessctl init profile ~/Workspaces/<consumer> --plan
harnessctl init profile ~/Workspaces/<consumer> --id <consumer> --host-mode dual-ide

# 3. verify the install
harnessctl host-pack status ~/Workspaces/<consumer>

# 4. prove the pack is standalone (no server needed)
printf '{"hook_event_name":"preToolUse","tool_name":"Write","tool_input":{"file_path":"<protected>","contents":"x"}}' \
  | python3 ~/Workspaces/<consumer>/.cursor/hooks/guard-write.py

# 5. reload the IDE window, then prompt a turn

# 6. after a profile change
harnessctl host-pack refresh ~/Workspaces/<consumer>
#    …and reload the window again
```
