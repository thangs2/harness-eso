# Docker deployment

The observe plane and the Console both run as containers. This is the supported deployment; running
them from the checkout is for development.

## Images

| Image | Dockerfile | Contains |
|---|---|---|
| `mu/harness-observe:local` | `docker/observatory.Dockerfile` | API + ingest + **bundled Observatory SPA** |
| `mu/harness-console:local` | `docker/console.Dockerfile` | Console API + wizard SPA |

Both are multi-stage: a `bun` build stage installs dependencies and builds the SPA, and the runtime
stage copies only what runs. The Observatory image serves its SPA from the same process as the API, so
there is one port and no separate static host.

The observe image's entrypoint is:

```
bun packages/harness-observe-server/src/server.mjs --root /data/repo --port 8792
```

## Operator entry points

```bash
docker/observatory.sh build              # host build:observatory, then compose build
docker/observatory.sh up [consumer]      # compose up; a path with harness.config.json sets HARNESS_REPO_ROOT
docker/observatory.sh down
docker/observatory.sh restart [consumer]
docker/observatory.sh status | health | logs | smoke
```

`powershell docker/observatory.ps1 …` is the Windows equivalent — same commands; use the platform script.

These scripts are thin: they forward to
`packages/harness-cli/src/observatory-cmd.mjs`. Read that file if a script's behaviour is unclear.

### `smoke`

`smoke` performs health + ingest + a requests sanity check. Use it after every deploy — it catches the
class of failure where the container is up and serving, but ingesting nothing.

## Required environment

The compose file **requires** two variables (it fails loudly rather than guessing):

| Variable | Example | Meaning |
|---|---|---|
| `HARNESS_REPO_ROOT` | `$HOME/Workspaces/<consumer>` | the consumer to mount read-only at `/data/repo` |
| `HARNESS_AGENT_ROOT` | `$HOME/Workspaces` | the agent workspace root, mounted at `/agent-repos` |

Optional:

| Variable | Default | Meaning |
|---|---|---|
| `HARNESS_OBSERVE_PORT` | `8792` | host port |
| `HARNESS_PRODUCT_STATE_HOST` | `$HOME/.harness` | what `/data/product-state` is bind-mounted from |
| `HARNESS_CURSOR_HOME` | `$HOME/.cursor` | transcripts, mounted read-only at `/host-cursor` |
| `COMPOSE_PROJECT_NAME` | — | set this to run several consumers side by side |

## Mounts, and why each is what it is

| Host | Container | Mode | Purpose |
|---|---|---|---|
| `HARNESS_REPO_ROOT` | `/data/repo` | **ro** | config, hooks, policy |
| volume `observe-data` | `/data/observe` | rw | per-project databases |
| `HARNESS_PRODUCT_STATE_HOST` | `/data/product-state` | rw | registry, consent, attestations, MCP ledger |
| `HARNESS_AGENT_ROOT` | `/agent-repos` | rw | agent workspaces |
| `HARNESS_CURSOR_HOME` | `/host-cursor` | ro | transcripts |

Three of these carry a decision:

**The consumer is read-only.** A bind-mounted SQLite database written from a macOS host into a Linux
container is what corrupted one. The consumer is an *input*.

**Product state is not the checkout.** It used to be mounted from the product repo, which made the
running stack depend on where the source tree sat. Mounting the operator's `~/.harness` instead means
the registry survives `git clean`, a branch switch, or moving the checkout.

**Product state carries the MCP usage ledger.** That is deliberate: the host-side MCP server and this
container both resolve the ledger through product state, so neither needs to know the other's layout.
Putting the ledger under `HARNESS_DATA_ROOT` would work locally and fail here — that root is a **named
volume**, a container-only filesystem the host server cannot see.

## One container per consumer

```bash
# primary consumer
HARNESS_OBSERVE_PORT=8792 ./docker/observatory.sh up ~/Workspaces/<consumer>

# another project, different port
HARNESS_OBSERVE_PORT=8794 COMPOSE_PROJECT_NAME=harness-observe-8794 \
  ./docker/observatory.sh up ~/Workspaces/<other>
```

The Console is the alternative and is what the operator UI is for: it registers projects, provisions
them and tracks their ports, so one Observatory can be told which project it serves.

## First `up` starts an empty database

Worth stating because it looks like data loss. Databases live in the `observe-data` **volume**, not in
the consumer, so a fresh volume means a fresh database, and the requests appear as ingest re-reads the
transcripts. It is a re-ingest, not a loss — but the wall clock time is real.

Migrating a recovered database once:

```bash
docker compose -f compose.harness.yml run --rm -v observe-data:/data/observe observe-server \
  sh -c 'mkdir -p /data/observe/<projectId> && cp /path/on/host/harness.db /data/observe/<projectId>/harness.db'
```

## Rebuild after code changes

```bash
./docker/observatory.sh build
./docker/observatory.sh restart
```

`build` runs the host SPA build first, so the image picks up the current `dist/`. If the UI looks
unchanged after a code change, check that step ran — the container serves a **built** bundle, and a
stale bundle looks exactly like a fix that did not work.

## Health and diagnosis

| Command | Tells you |
|---|---|
| `docker/observatory.sh health` | `GET /health` |
| `docker/observatory.sh smoke` | health + ingest + requests |
| `docker/observatory.sh logs` | container logs |
| `GET /api/ingest/status` | ingest counters and last-cycle report |

Common container-only failures:

| Symptom | Likely cause |
|---|---|
| starts, serves, ingests nothing | the consumer mount is empty or has no `harness.config.json`, or transcripts are not mounted |
| requests exist but no events | hook trace not mounted (the trace lives in the **consumer**, so it needs the repo mount) |
| Brain token totals always "not reported" | the MCP ledger is not reaching `/data/product-state` |
| `up` refuses to start | `HARNESS_REPO_ROOT` or `HARNESS_AGENT_ROOT` unset |

## Docker versus development

| | Docker | checkout |
|---|---|---|
| data root | `/data/observe` (volume) | `~/.harness/observe` |
| database | inside the volume | on the host filesystem |
| UI | built into the image | `dist/` served by the local server |
| port | `HARNESS_OBSERVE_PORT` | `--port` |

Their databases are **separate**, so the same consumer shows different data in the two. Do not run
`scripts/dev-observe.sh` while the Docker Observatory is up: the databases no longer collide, but the
port does.
