# Repo conventions

## Language and module system

- **ESM only**, `.mjs`. No CommonJS, no TypeScript in the server packages — the SPA is TSX.
- Node builtins are imported with the `node:` prefix (`import fs from 'node:fs'`).
- Bun is the package manager (workspaces + `bun.lock`). `bun install`, never `npm`/`yarn`.

## Package layout

```
packages/<name>/
  package.json      # name @mu/harness-<name>, exports map
  src/*.mjs         # implementation, one concern per file
  src/*.test.mjs    # tests colocated (only some packages have them)
```

`exports` maps decide what importers may reach. Adding a new public symbol means:

1. implement it,
2. export it from the package's entry (`index.mjs`),
3. if a **hook** may import it, export it from **`pure.mjs`** as well.

Forgetting step 3 fails `bun run build:host-pack` with the exact missing symbol. That is intentional —
see [`02.invariants.md`](./02.invariants.md) #4.

## Comments

This repo has an unusually high comment density, and it is a convention rather than an accident. A
comment here is expected to carry:

- **why** the code is the way it is, especially when the obvious alternative is wrong;
- the **failure** that produced a non-obvious rule, with the number of the defect (`F42`) where one
  exists;
- **what is not claimed**, when a guarantee is weaker than it looks.

```js
// GOOD — a reader cannot re-introduce the bug by "simplifying" this
/*
 * `repaired > 0` forces a full recompute. Reporting a correction as a repair is what makes a
 * re-attribution revisit the turn's files and checks — none of which would be updated under a narrow
 * scope. Measured: 3,438 events were mis-filed before this.
 */

// BAD — restates the code
// increment the counter
```

Do not add a comment that only narrates the next line. The code already says that.

## Tests

| Suite | Runner | Location |
|---|---|---|
| product logic | `node:test` via Bun | `qc/*.test.mjs`, `packages/*/src/*.test.mjs` |
| SPA | Vitest | `packages/harness-observatory/src/**/*.test.tsx` |

Run `bun run test` — **not** bare `bun test`. `bunfig.toml` pins `[test] root = "./qc"`, and that
setting overrides paths passed on the command line, so `bun test <dir>` silently runs only `qc`.
`scripts/run-tests.mjs` runs each suite from inside its own directory, which is the only way to reach
the others (`bun test --root` is not a supported flag).

### What a test here is expected to do

Tests in this repo are written to **discriminate**, not to cover:

- A regression test should **fail when the fix is reverted**. Both the attribution and the shell-write
  tests were verified this way — temporarily restore the bug, watch the test go red, restore the fix.
  A test that passes either way is documentation, not a test.
- Assert the **specific wrong behaviour** you are preventing, with a message that names it:
  `assert.equal(eventRequest(db,'Grep'), 'conv:1', 'its own generation is first-hand evidence, a time guess is not')`.
- Prefer a **fixture that recreates the production shape** over a convenient one. The tests that
  actually caught bugs here did so because they reproduced a race or a legacy state (a placeholder
  generation, a null `request_id`, an ESO row carrying its bundle in the Jev column).

## Commits

- Only when asked. Do not commit `.harness/` (local state) from the product repo.
- A commit that changes behaviour should name the defect number in the message if one exists.

## Documentation

Two roots, different jobs:

| Root | Holds | Rule |
|---|---|---|
| `documents/` | what the system is | update when **behaviour** changes |
| `docs/` | the defect log + operator runbooks | append-only; **never** rewrite history here |

When you fix a defect: append a section to `docs/04.standalone-revamp-wbs.md` with the symptom, the
measured evidence, the cause, the fix, and what remains. Then update the affected `documents/` page if
the *described behaviour* changed. The defect log is the argument; `documents/` is the conclusion.

Every claim in the defect log should be **measured**. "Seems fixed" is not an entry; "3,438 rows, now 0
resolve-able" is.

### The docgraph index is build output, and it goes stale silently

`.docgraph/docgraph.json` is gitignored and, unlike `.codegraph/`, has **no daemon** — codegraph
auto-syncs on every MCP call, docgraph is rebuilt only when someone types `docgraph build`. It was
nine days old on 2026-10-23 (G-20), which meant the "docgraph first" rule in `AGENTS.md` was pointing
at a corpus that did not contain the documents written that week.

After editing anything the scope covers, either rebuild or ask:

```bash
docgraph build            # regenerate the artifact
bun run docgraph:check    # exit 1 when covered files changed after generated_at
```

The check reads `docgraph.scope` itself — `path:` roots, `ext:`, `exclude:` — so a doc outside the
scope is not "missing". It never edits the index; the fix it prints is the fix.

## Adding a migration

Append-only, numbered, never edit an applied one. If the migration changes what a **derived** table
means, clear those tables in the same migration — the corrected code rebuilds them, and the next pass is
full because `migrations.length > 0` participates in the change gate. See
[`../03.state-and-contracts/02.data-model.md`](../03.state-and-contracts/02.data-model.md) for the
examples already in the repo.

## Adding a hook

1. Implement `run()` in `packages/harness-host-generic/src/<name>-hook.mjs`.
2. Register it in `dispatch.mjs` with an explicit `kind` (`guard` or `telemetry`) — that choice decides
   the failure posture.
3. Wire it in the profile(s) under `profiles/host/*.json`, with an `id`.
4. If it is a **query** rather than a guard (prints data, not a permission payload), do **not** wire it
   to an event; document who calls it instead.
5. `bun run build:host-pack`, then `host-pack refresh` on a consumer, then **reload the window**.
6. Never import the foundation root from a hook — only `pure`.

## Adding a path tier entry

Add it to the **consumer's** `decision-policy.json`, not to product code. If the entry is a name
**prefix**, write the `*` (`backend/mu-*`); a bare `backend/mu-` matches exactly one path.

## Environment variables that alter behaviour

Worth knowing, because they make a repro non-reproducible:

| Variable | Effect |
|---|---|
| `HARNESS_PRODUCT_STATE_DIR` | move product state (tests use this to sandbox) |
| `HARNESS_DATA_ROOT` / `HARNESS_SQLITE_PATH` | database location |
| `DEEPSEEK_USAGE_LEDGER` / `DEEPSEEK_FRAME_LOG` | MCP ledger paths |
| `HARNESS_SESSION_DIR` | session dir for a host whose sessions live outside the repo (DSH: `~/.dsh/sessions`). Must be absolute and outside the repo, or both `guard-write.py` and the pack refuse it |
| `HARNESS_STAMP_WRITES` | `exempt` = the agent may write the Brain stamp without the host's approval prompt. Same as `eso.cognition.stampWrites` in policy — opt-in, off by default |
| `HARNESS_MCP_PROMPT_BACKFILL_LIMIT` | history walk bound |
| `HARNESS_INGEST_POLL_MS` | poll interval |
| `guards.unavailable` (policy, not env) | guard failure posture |

### Before blaming the Brain gate: `harnessctl check brain`

The Brain gate's primary evidence is the DeepSeek usage ledger in product state, and its one disabling
failure is silent — a sandbox that stops the MCP child writing that file leaves `brain_attested()`
returning `{}`, so the deny names *Brain* while the actual missing thing is a file nobody wrote. Measured
on DSH: the ledger's newest record was three days old and nothing said so.

`harnessctl check brain [--json]` answers, separately: does the ledger exist, how old is its newest Brain
record, and does the product resolve the same path this check did. A `ledger-path-disagreement` finding
means `DEEPSEEK_USAGE_LEDGER` is set for some readers and not others — the fix is one absolute path that
the MCP child **and** the hook can both reach (never inside the repo: the agent can write there).
Exit code 1 on any finding other than malformed lines.

**A host whose sandbox blocks the ledger must not be pointed at another file.** DSH gives the MCP child
no write access to product state, and the obvious remedies — move the ledger into the workspace, widen the
sandbox — both end with the *gated party* able to append evidence. So that host records the call itself
instead: `harness-eso-dsh` listens on `tools/post-execute`, and a Brain-tier tool that returned without an
error mints `brain` inside the same product-state attestation the evidence gate already reads. The check
reports that as a `witness` line rather than complaining about a ledger the host does not use. Pointing
`DEEPSEEK_USAGE_LEDGER` at a workspace path is **not** the fix for this case.
