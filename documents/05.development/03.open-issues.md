# Open issues

The honest state. Read this before planning work, and treat everything here as something a previous
reader needed to know.

Each entry says what is wrong, **how it was established**, and what a fix would have to solve. Where an
entry has a defect number, the full measured history is in `docs/04.standalone-revamp-wbs.md` — this is
the summary, that is the argument.

## 1. A freshly provisioned consumer gets **no write gate**

**Severity: high. This is a gap in the product's completeness, not a bug in existing code.**

Established by reading the provision plan and a real consumer's wiring side by side:

| Wired on a provisioned consumer | Authored by |
|---|---|
| `preflight`, `route`, `gap-tracker`, `post-tool-hint`, `pre-compact`, `guard-brain` | **pack** |
| `guard-shell` (static denies + decision facade) | **pack** |
| **`guard-write.py`** — path tiers, secrets, evidence, Brain, consent | **consumer** |
| **`guard-shell.py`** — protected-path writes via shell | **consumer** |

`init profile` writes the pack, `hooks.json`, `decision-policy.json`, `integrations.json`,
`sidecar.env` and `harness.config.json`. It does **not** write a `guard-write.py`, because the pack
deliberately ships no write gate (`F26`: a pack copy checked evidence but not paths, so it blocked
ordinary `src/` edits while allowing edits to the consumer's most protected files).

The consequence: **a consumer that runs `init profile` on a clean repo ends up with no path protection
at all.** The policy file it receives names protected paths, and nothing enforces them — the file exists
and is inert.

The reference implementations currently live in a provisioned consumer
(`x79/.cursor/hooks/guard-write.py`, `guard-shell.py`, ~400 lines each, byte-identical between the two
IDE trees). That is the wrong place for them, and it is the one thing in this project that is genuinely
**not** standalone.

What a fix has to solve:

- the guards must be **templates the product ships** (so provisioning is complete), while still being
  **consumer-owned at runtime** (so an operator can adapt policy);
- the protection list they read must stay in consumer policy (already solved: `paths` in
  `decision-policy.json`) rather than in the guard source;
- the two IDE copies must stay byte-identical, which they currently achieve by being copied, and which
  the `HARNESS_DIR`-derived session path depends on;
- upgrading a template must not overwrite an operator's edits — the same three-way problem the hook
  merge already solves, and the same solution applies.

`paths.gated` in the default policy already lists the consumer guard files, so a guard that exists is
protected from being silently rewritten. Nothing creates it.

## 2. A model call can be dispatched by the IDE and never arrive at the server

**Severity: high. Unresolved. Now instrumented.**

Observed **three times**: Cursor renders an `mcpToolCall bubble` for the model server, and the call then
leaves no trace anywhere.

Established by eliminating every alternative:

| Hypothesis | Ruled out by |
|---|---|
| the server was down | process alive, no respawn |
| the call was still streaming | **no TCP socket** on the server process |
| the API failed | no server stderr line at all |
| the IDE timed out | no idle/timeout entry for that server |
| the server cannot handle this call | **a probe outside the IDE: 33.6 s, HTTP 200, 23,139 reasoning chars, ledger row written** |
| the transport was suspended | that mechanism exists but applies only to another server here |

The strongest evidence is that the server's ledger write is in an **unconditional `finally`**: an absent
record proves `callDeepSeek` never ran, so `handleToolCall` never received a request. The loss is between
"the IDE rendered the call" and "the stdio server received the frame".

**Instrument already installed** (`F50`) — the server now writes one row per **inbound frame** to
`<product state>/deepseek-frames.jsonl`:

```json
{"kind":"tools/call","tool":"ask_deepseek_flash","promptChars":356,"brainPrefix":true,"progressToken":false}
```

plus `{"kind":"heartbeat-failed"}` when a progress notification cannot be sent — which is the shape of
"the client gave up".

**The next occurrence is decidable:**

| frames log | conclusion |
|---|---|
| has a row | the frame arrived; the fault is server-side |
| no row | the frame was never delivered; the fault is the IDE, and this is evidence for a Cursor report |

**A strong hypothesis to test at the same time:** the probe showed `progressToken: false` when the
client sends no token. If Cursor also sends none, `startProgressHeartbeat` is a **no-op**, and any call
longer than Cursor's idle clock is cut with no keep-alive. The `progressToken` field in the frame log
answers this directly.

## 3. The `ask` tier is a deny with a good message, not a real prompt

**Severity: medium. The consent mechanism is real; the *asking* is not.**

Cursor's hook contract accepts only `allow` and `deny` — verified from the shipped bundle, which warns:

```
'ask' permission for subagentStart hooks is not yet implemented. Use 'allow' or 'deny' instead.
```

So a hook cannot pause a turn and ask a human. The `ask` tier therefore behaves as **gated** until a
consent record exists, and its deny message names the Console call that would grant one.

What exists and works: consent records in product state, `.harness`-level policy, guard enforcement on
**both** channels, expiry, scope, revoke, and an HTTP API.

What is missing:

- **no Console UI.** The API is complete (`POST|GET|DELETE /api/projects/:id/consent`) but the SPA has no
  button, so granting consent today is a `curl`. Verified: the Console SPA contains no consent UI.
- **no mid-turn flow.** A human must approve *before* the agent retries; there is no mechanism for the
  agent to request and wait.

Neither is hard, and neither is architectural — the hard part (a trust location the agent cannot write)
is done.

## 4. Guards are not a sandbox, and this is not fixable in-product

**Severity: by design. Documented so nobody overclaims it.**

An agent with shell access runs as the same user. It can read every file a guard reads, and could write
one if a guard were bypassed. There is no process confinement; enforcement covers the operations the IDE
routes through hooks.

The achievable goal, which is what the current design delivers:

1. the **honest path** no longer requires the agent to write its own permission;
2. the **casual forgery** — editing a stamp next to files the agent legitimately writes — no longer works,
   because the guard prefers a product-state record;
3. deviations are **attributable**.

The next real step, if a stronger guarantee is wanted, is for the guard to **ask a process** (Console or
observe plane) over a socket, so the decision never touches a filesystem the agent can write. Blocked on
issue #2: the observe plane's knowledge of model calls comes from the transcript, which is asynchronous
and records intent rather than completion. See the closure argument in
[`../02.runtime/03.consent-and-attestations.md`](../02.runtime/03.consent-and-attestations.md).

## 5. ~3,400 events remain attributed by time window alone

**Severity: low. Missing data, not a logic error.**

After the attribution fix, the remaining events whose generation disagrees with their request all share
one property: **their generation resolves to no request and has no captured prompt** — the turn was never
seen by ingest. For those, the turn window is the only signal available, and using it is the designed
behaviour.

Do not "fix" this by loosening the rules. The count is a measure of how many turns the harness never
captured, which is a hook-coverage question, not an ingest one.

**Diagnostic** to separate the two classes is in
[`../04.operations/04.troubleshooting.md`](../04.operations/04.troubleshooting.md) (the "turn shows 2
tool calls" section) — the query that matters is whether the disagreeing events resolve to a real
request.

## 6. A consumer's Brain attestation is project-blind

**Severity: low, and inherent to MCP.**

The ledger is machine-wide, because an MCP server receives a prompt and nothing else — no conversation,
no generation. So the gate can attest *"a Brain call completed recently"*, not *"for this turn"*. A Brain
call in another project can satisfy a gate here.

The accurate per-turn join exists (`sha256(prompt)` between `mcp_prompt` and `mcp_call`) but is not
reachable at gate time, and lags by the poll interval. This is a property of the MCP contract, not of
the implementation; a fix would need the IDE to pass correlation metadata, which it does not.

## 7. The session-stamp fallback still exists

**Severity: low. Intentional during migration.**

`guard-write.py` prefers the product-state attestation and falls back to the session-dir stamp when it is
absent — which covers a consumer whose pack predates the change. The fallback is the **agent-writable**
path, so while it exists, the hardening is conditional on the pack being current.

Removing it is the correct end state and requires: every consumer refreshed, and the fallback's removal
recorded (a consumer that has not refreshed would lose its gate entirely — so this must be a deliberate
rollout, not a cleanup).

## 8. `enforceWrites` is currently `off` on the dev consumer

**Severity: informational. An operator decision, not a defect.**

The dev consumer's policy originally said `"observe"` — a value that is valid for `eso.mode` but never
was for `enforceWrites`, and which was silently coerced to the **strictest** posture (`F24`). It has been
set to `off` deliberately, which disables the **ESO evidence gate** while leaving the Brain gate, consent
and locked paths in force.

Consequence to expect when reading a deny message: the gate named is `Brain gate`, not `ESO gate`. That
is the policy, not a regression.

## 9. Two documentation roots

**Severity: cosmetic, but it will confuse a reader.**

`documents/` (this pack) describes the system; `docs/` holds the live defect log and operator runbooks.
They overlap in places. `docs/04` is the authority on *history*; this pack is the authority on *current
behaviour*.

If you find them contradicting each other about behaviour, this pack is right and `docs/04` is a record
of what used to be true — fix `docs/04` only if it is actively misleading.

## 10. The Docker operator surface exists four times

**Severity: medium. Two documented commands are already broken on one platform.**

`docker/`, the two compose files, the root `harness` wrapper and the npm `compose:*` aliases expose four
independent ways to run the same two containers, synchronised by hand. `docker/process/` is a fifth
layer over them and is referenced by nothing executable.

It has already drifted: `console.ps1` is missing `down`/`restart`/`status`/`logs` that
`docker/README.md` documents, and still implements a `dev` command that `console.sh` deliberately
removed. Separately, `install.sh` seeds a repo-local `.harness/workspace.json` that
`productStateDir()` does not resolve to — re-creating the legacy path the design migrated away from.

This is invariant **A1** (one source of truth per fact) applied to the operator surface: the command
set is a fact with four copies and no import.

Full register, with evidence, verdicts and a sequencing plan:
[`04.docker-tech-debt.md`](./04.docker-tech-debt.md).
