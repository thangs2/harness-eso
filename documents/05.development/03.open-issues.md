## 12. Nothing proves the product runs on Windows [OPEN — P1–P3 fixed, CI matrix added, not yet run on GitHub]

**Severity: high until a Windows runner exists. The three known breakages are fixed; what remains is
that nothing would have caught them, and nothing yet catches the next one.**

macOS, Linux and Windows are all in scope. The suite runs `bun test` on **one** host, and neither the
four shell entrypoints nor the host profiles had any cross-platform coverage. That is why the following
survived: none of them was visible from a green suite on macOS. Each was re-confirmed against this tree
by grep, not from memory.

### Confirmed breakages — all fixed 2026-10-22

| # | What broke | Where | Why | Now |
|---|---|---|---|---|
| P1 | **every hook** | 29 command literals in `profiles/host/{cursor,agents,claude}-superset.json`; plus `host-install.mjs` tracer | each command was `bash -lc '… exec node …'`; Windows has no `bash` on PATH, so the hook exits 127 and a `failClosed` entry blocks the turn | commands are `node .harness/host-pack/harness-hook.mjs --hook X --tree Y` — no shell, no `export`, no `cd ..` |
| P2 | **all four operator scripts** | `deploy.sh`, `provision.sh`, `verify-consumer.sh`, `console.sh` | the `sh` → `bash` re-exec was hardcoded to `/bin/bash`, which Git Bash does not provide | prefers `bash` from PATH, then conventional absolute paths one at a time, then exits `2` with a sentence |
| P3 | **route / trace spine** | `route-hook.mjs` → `resolveRouteHookPy()` | spawned `python3`; Windows has `python.exe`/`py.exe`, the spawn failed with ENOENT, and the caller fails **open** — the trace vanished with no error and no counter | `resolvePython()` probes `HARNESS_PYTHON`, `python3`, `python`, `py`; a missing interpreter now prints a diagnosis instead of failing silently |

P2 was introduced while fixing the port bugs (§11) — a change that looked correct, passed review, and
was wrong on two of the three target OSes.

### The bug the fix itself exposed

Making the pack runnable directly (`node …`) broke the dispatcher's entry guard. It compared
`import.meta.url` against `pathToFileURL(process.argv[1])`, and on macOS `os.tmpdir()` is
`/var/folders/…`, a symlink to `/private/var/folders/…` — so the two strings differed, the module loaded
and defined everything, and **exited 0 with no output**: not a deny, not an allow, silence that a host
reads as a crash. Both sides now go through `realpathSync`, and an unresolvable path falls back to
running rather than to silence.

This is the failure mode the whole issue is about: a hook that produces nothing looks exactly like a
hook that agreed. Ten tests caught it, which is the argument for the coverage existing.

### Suspected, not yet established (P4–P6)

These are the ones the matrix is expected to settle. None has been reproduced, because no run on Windows
has happened yet.

| # | Risk | Where |
|---|---|---|
| P4 | guard scripts may use POSIX-only APIs (`fcntl`, `signal.SIGKILL`, `os.getuid()`, `/tmp`) | `profiles/templates/hooks/guard-{write,shell}.py` |
| P5 | a host path is passed straight into the compose bind mount — `C:\Users\…` is not a valid bind source for Docker Desktop | `observatory-cmd.mjs`, `console-cmd.mjs` |
| P6 | the same for the observe SQLite volume path | `observatory-cmd.mjs` |

P1 also changes how one old finding should be read: the baplatform report described `exit 127` on
**every** shell call. That is P1's exact signature. The report blamed a bare `python`; the tree emitted
no such command. If that session ran on Windows the symptom was real and the cause was `bash`. Not
established either way — the finding is **unproven**, not disproven.

### What now holds the line

| Check | Fails when | State |
|---|---|---|
| profile lint | a `command` in `profiles/host/*.json` invokes `bash`/`sh`, or `export`s a variable, or names a non-pack interpreter outside the one asserted exception | **done**, `qc/hook-portability.test.mjs` |
| hook smoke without a shell | any distinct `--hook` value produces no JSON decision when `PATH` contains no bash | **done**, same file |
| entrypoint lint | a `.sh` runs an absolute interpreter path (`/bin/bash`; `/usr/bin/env` is fine) | **done**, `qc/entrypoint-scripts.test.mjs` |
| entrypoint `sh` re-exec | `sh deploy.sh --help` still works, and the re-exec does not assume `/bin/bash` | **done**, same file |
| CI matrix | `bun test` on `ubuntu-latest`, `macos-latest`, **`windows-latest`** | **done**, `.github/workflows/ci.yml` (4 jobs) |
| smoke | the `.sh` entrypoints answer `--help` under `sh`, `--plan` on an empty registry exits 0 or 2, and `harness.ps1` forwards argv on Windows | **done**, same workflow, `entrypoint-smoke` job |
| workflow self-check | the matrix loses an OS, tabs appear in the YAML, or the hook smoke runs before the pack is built | **done**, `qc/ci-workflow.test.mjs` |

The lints are static-string checks, and one of them was written twice: the first entrypoint lint flagged
the `/bin/bash` **fallback** that is the fix. A lint that has never been run against the tree it guards
is a guess. The workflow has the same hazard one level up — a YAML typo fails *the gate* rather than the
code, with no line number, and the next instinct is to disable the gate — which is why
`qc/ci-workflow.test.mjs` pins the job set, the three-OS matrix, and the build-before-smoke order.

**Not yet proven:** the workflow has been validated locally (structure, the assertions above, and every
command it runs was executed on macOS) but has **not run on GitHub**, so `windows-latest` behaviour is
still a claim. P4–P6 below are the risks that only that run can settle.

### What still does not work on Windows

Two commands stay Python by design, because the pack has no replacement for either:

- `python3 .claude/hooks/guard-write.py` (claude profile) — the write gate checks the **path** allowlist
  as well as the evidence stamp; the pack copy did not, and wiring it froze all editing on consumers
  whose evidence sat below threshold (`F26`).
- `python3 hooks/pre-tool-use.py` (`host-install.mjs`, spelled relative to `.agents/` because that is the
  cwd Antigravity spawns it with — see `F6`) — the Antigravity dispatcher that runs write-then-shell from
  one stdin read.

A command literal cannot resolve an interpreter name, so both need `python` on PATH or a `python3` shim
on Windows. That is a documented prerequisite, not something a string can fix; the alternative is a
launcher per interpreter, which is more moving parts than the guard is worth.

### What a `<tree>` change would have to cover

The interpreter strings had three sources, and changing one was not a fix:

1. `profiles/host/*.json` — the hook command literals themselves (**changed**);
2. `host-install.mjs` — `ensureConsumerGuards()` copies the `.py` files but emits no command, so the
   effective command came from the host's merged settings and could outlive a profile change
   (**re-provisioned consumers converge, because the merge matches on `--hook`**);
3. `resolveRouteHookPy()` — a separate spawn that does not go through the profile at all (**changed**).

## 2. A model call can be dispatched by the IDE and never arrive at the server

**Severity: high. Unresolved. Now instrumented.**

Observed **three times**: Cursor renders an `mcpToolCall` bubble for the model server, and the call then
leaves no trace anywhere.

Established by eliminating every alternative:

| Hypothesis | Ruled out by |
|---|---|
| the server was down | process alive, no respawn |
| the call was still streaming | **no TCP socket** on the server process |
| the API failed | no server stderr line at all |
| the IDE timed out | no idle/timeout entry for that server |
| the server cannot handle this call | **a probe outside the IDE: 33.6 s, HTTP 200, 23,139 reasoning chars, ledger row written** |
| the transport was suspended | that mechanism exists but applies only to another server here |

The strongest evidence is that the server's ledger write is in an **unconditional `finally`**: an absent
record proves `callDeepSeek` never ran, so `handleToolCall` never received a request. The loss is between
"the IDE rendered the call" and "the stdio server received the frame".

**Instrument already installed** (`F50`) — the server writes one row per **inbound frame** to
`<product state>/deepseek-frames.jsonl`:

```json
{"kind":"tools/call","tool":"ask_deepseek_flash","promptChars":356,"brainPrefix":true,"progressToken":false}
```

plus `{"kind":"heartbeat-failed"}` when a progress notification cannot be sent — which is the shape of
"the client gave up".

**The next occurrence is decidable:**

| frames log | conclusion |
|---|---|
| has a row | the frame arrived; the fault is server-side |
| no row | the frame was never delivered; the fault is the IDE, and this is evidence for a Cursor report |

**A strong hypothesis to test at the same time:** the probe showed `progressToken: false` when the
client sends no token. If Cursor also sends none, `startProgressHeartbeat` is a **no-op**, and any call
longer than Cursor's idle clock is cut with no keep-alive. The `progressToken` field in the frame log
answers this directly.

## 3. The `ask` tier is a deny with a good message, not a real prompt [PARTIAL]

**Severity: medium. The consent mechanism and Console UI are real; mid-turn prompting remains limited by
the IDE contract.**

Cursor's hook contract accepts only `allow` and `deny` — verified from the shipped bundle, which warns:

```
'ask' permission for subagentStart hooks is not yet implemented. Use 'allow' or 'deny' instead.
```

So a hook cannot pause a turn and ask a human. The `ask` tier therefore behaves as **gated** until a
consent record exists, and its deny message names the Console call that would grant one.

What exists and works:

- consent records in product state (`<state>/consent/<projectId>.json`);
- guard enforcement on **both** channels (`guard-write.py` and `guard-shell.py`);
- full REST API (`POST|GET|DELETE /api/projects/:id/consent`);
- Console UI at `:8791` — `ConsentManagementPanel` on `ConfigPage`: inspect active path consents,
  grant timed consents with a custom duration, revoke with one click.

What remains: **mid-turn flow.** A human must approve before the agent retries; there is no hook
mechanism for the agent to pause mid-turn and await input.

## 4. Guards are not a sandbox, and this is not fixable in-product

**Severity: by design. Documented so nobody overclaims it.**

An agent with shell access runs as the same user. It can read every file a guard reads, and could write
one if a guard were bypassed. There is no process confinement; enforcement covers the operations the IDE
routes through hooks.

The achievable goal, which is what the current design delivers:

1. the **honest path** no longer requires the agent to write its own permission;
2. the **casual forgery** — editing a stamp next to files the agent legitimately writes — no longer
   works, because the guard prefers a product-state record;
3. deviations are **attributable**.

The next real step, if a stronger guarantee is wanted, is for the guard to **ask a process** (Console or
observe plane) over a socket, so the decision never touches a filesystem the agent can write. Blocked on
issue #2: the observe plane's knowledge of model calls comes from the transcript, which is asynchronous
and records intent rather than completion. See the closure argument in
[`../02.runtime/03.consent-and-attestations.md`](../02.runtime/03.consent-and-attestations.md).

## 5. ~3,400 events remain attributed by time window alone

**Severity: low. Missing data, not a logic error.**

After the attribution fix, the remaining events whose generation disagrees with their request all share
one property: **their generation resolves to no request and has no captured prompt** — the turn was
never seen by ingest. For those, the turn window is the only signal available, and using it is the
designed behaviour.

Do not "fix" this by loosening the rules. The count measures how many turns the harness never captured,
which is a hook-coverage question, not an ingest one.

**Diagnostic** to separate the two classes is in
[`../04.operations/04.troubleshooting.md`](../04.operations/04.troubleshooting.md) (the "turn shows 2
tool calls" section) — the query that matters is whether the disagreeing events resolve to a real
request.

## 6. A consumer's Brain attestation is project-blind

**Severity: low, and inherent to MCP.**

The ledger is machine-wide, because an MCP server receives a prompt and nothing else — no conversation,
no generation. So the gate can attest *"a Brain call completed recently"*, not *"for this turn"*. A Brain
call in another project can satisfy a gate here.

The accurate per-turn join exists (`sha256(prompt)` between `mcp_prompt` and `mcp_call`) but is not
reachable at gate time, and lags by the poll interval. This is a property of the MCP contract, not of the
implementation; a fix would need the IDE to pass correlation metadata, which it does not.

## 7. The session-stamp fallback still exists [CONFIGURED & HARDENED]

**Severity: low, mitigated, default still open.** `guard-write.py` prefers the product-state attestation
and includes a configurable fallback gate, `allow_session_stamp_fallback()`.

While `allowSessionStampFallback` defaults to `true` during the transition — so unmigrated consumers keep
working — strict operators can disable the agent-writable session stamp by setting
`"allowSessionStampFallback": false` in `.harness/decision-policy.json`, or
`HARNESS_ALLOW_SESSION_STAMP_FALLBACK=0` in the environment. When disabled, `guard-write.py` enforces
pure product-state attestations for both ESO evidence and Brain call records, with zero fallback to
agent-writable files. Tested in `qc/init-profile.test.mjs`.

The residual risk is the default, not the mechanism: a consumer that never sets the flag keeps the
fallback.

## 8. `enforceWrites` is `off` on the dev consumer

**Severity: informational. An operator decision, not a defect.**

The dev consumer's policy originally said `"observe"` — a value valid for `eso.mode` but never for
`enforceWrites`, and one that was silently coerced to the **strictest** posture (`F24`). It is now `off`
deliberately, which disables the **ESO evidence gate** while leaving the Brain gate, consent and locked
paths in force.

Consequence when reading a deny message: the gate named is `Brain gate`, not `ESO gate`. That is the
policy, not a regression.
