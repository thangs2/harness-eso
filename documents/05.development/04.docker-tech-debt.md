- **D6:** Labeled Console URL in `./harness up` honestly (`(bật riêng: ./harness console)`).

- **D3:** Moved daemon prereq check into shell scripts, added `/api/tenant` to `observatory smoke`, and deleted `docker/process/`.
- **D4 + D5:** Pointed `install.sh` to `observatory build`, deleted `observe-cmd.mjs` shim and deleted raw npm `compose:up`/`down`.
- **D8 + D9 + D10:** Refined `.dockerignore`, corrected Dockerfile comment, and deleted fossil `observe.sh` warnings.

Scope: everything that boots or drives the containers — `docker/`, the two compose files, the root
`harness` wrapper, `install.sh`, and the Docker-related npm scripts.

Nothing here is a correctness bug in the ingest spine or the gates. Two entries are real operator-facing
defects; the rest is duplication, and duplication is how the two defects happened.

## Why this exists

`docker/` is **16 files / 918 lines**, and `docker/process/` alone is **9 files / 221 lines**. Measured:

```bash
find docker -type f | wc -l          # 16
wc -l docker/process/* | tail -1     # 221 total
```

Most of that is a second and third way to do what one command already does. The cost is not the lines —
it is that **four command surfaces now have to be kept in agreement by hand**, and two of them have
already drifted (D1, D2).

This is the failure that invariant **A1** names: *"If two components must agree about a fact, they import
one implementation."* The operator surface is a fact with four copies and no import.

## D1. `console.ps1` silently lacks half its documented commands

**Severity: high — a documented command fails on Windows.**

`docker/README.md` documents the Console surface as:

```
| `down` / `restart` / `status` / `health` / `logs` | Compose lifecycle |
```

`console.sh` implements that. `console.ps1` does not — its parameter set is the whole surface:

```powershell
[ValidateSet('build', 'up', 'start', 'dev', 'health', 'help')]
```

Established by reading it: `docker/console.ps1:5`. So `console.ps1 down` fails at **parameter binding** —
an error and a non-zero exit, not a silent no-op (the switch has no `default`, but `ValidateSet` makes
that unreachable). Missing: `down`, `restart`, `status`, `logs`, `ps`.

Nothing about this is theoretical: `docker/process/02.console-up.ps1` starts the Console on Windows and
there is no supported way to stop it. The workaround is `docker compose -p harness-console down`, which
the operator has to reconstruct from the compose file.

**What a fix has to solve.** The two scripts must not be able to disagree. Adding the five commands by
hand fixes today's gap and recreates the mechanism — `console.ps1` was written against an older
`console.sh` and nothing detected the drift. Either (a) derive both from one command table, or (b) keep
only `compose` lifecycle in the `.ps1` and forward everything else to the same Node entrypoint the `.sh`
calls, so the surface lives in `console-cmd.mjs` and neither script owns it.

**Why it went unnoticed.** `observatory.ps1` is complete (`build up down restart status health logs
smoke`), so a Windows operator who only uses the Observatory never meets this. It is exactly the Console
that is broken, which is the one required to provision a consumer.

## D2. `console.ps1` still implements a command the `.sh` deliberately removed

`console.sh` answers `dev` with a deny and a pointer:

```bash
dev)
    die "dev mode removed from console.sh — use Docker: console.sh up (or local: node packages/harness-console-server/src/server.mjs)"
    ;;
```

`console.ps1` still **implements** it — `Cmd-Dev`, `docker/console.ps1:80-98`, 19 lines: `Ensure-ProductState`,
`Free-Port`, spawn `node …/console-server/src/server.mjs`, then Vite.

So the same command is refused on macOS/Linux and works on Windows. A removal that was applied to one
platform is not a removal.

**What a fix has to solve.** Decide which is true and make both match. Given the `.sh` message names the
supported alternatives, removing `Cmd-Dev` is the cheaper and more consistent answer — but it is a
**behaviour removal on Windows**, so it belongs in the same change as D1, not as a drive-by.

## D3. `docker/process/` is a third copy of the operator path

**Severity: medium. No product code depends on it.**

Established by searching every reference. `docker/process/` is named in exactly four files, all of them
prose or each other:

```
docker/README.md
docker/process/00.README.md
docker/process/01.observatory-up.sh
docs/04.standalone-revamp-wbs.md
```

No package, no test, no CLI, no profile. It is not part of the product's execution.

What the four scripts do, in full:

| Script | Body |
|---|---|
| `00.docker-check` | assert docker daemon + `bun` + `node_modules` |
| `01.observatory-up` | call `00`, then `observatory.sh build`, then `harness up`, then `curl /health` |
| `02.console-up` | `console.sh up` (plus three `Write-Host` lines) |
| `03.verify-observatory` | `curl /health`, then `curl /api/tenant` |

Every one of those steps is already reachable:

| Step | Existing command |
|---|---|
| docker daemon / bun / deps check | *nothing* — see below |
| build + up | `./harness up` (builds, then compose up) |
| health | `./harness health` |
| console | `./harness console` |
| health + ingest + requests sanity | `./docker/observatory.sh smoke` |

So the unique substance in 221 lines is **two things**: the prerequisite check in `00`, and the fact that
`03` curls `/api/tenant`.

`/api/tenant` is worth keeping: `smoke` does **not** cover it. Verified by reading `cmdSmoke`
(`packages/harness-cli/src/observatory-cmd.mjs:133-144`) — it calls `/health`,
`/api/ingest/status`, `POST /api/ingest/run`, `/api/requests?limit=5`. The tenant endpoint is the one
that proves the *consumer* is wired, which is precisely the post-provision question `03` exists to
answer.

**What a fix has to solve.** Preserve those two facts without keeping a numbered ladder:

- the prerequisite check belongs in `observatory.sh up` (fail before `docker compose build`, not after),
  or as a `harness doctor` the README can point at;
- the tenant check is one `curl` — document it in `docker/README.md` next to `smoke`, or add
  `/api/tenant` to `smoke`'s output.

Then `docker/process/` — and its 37-line README — goes away, and the operator has **one** sequence
(`install.sh` → `harness up` → `harness console`) instead of a numbered ceremony that shadows it.

**Note on what is *not* wrong here.** The scripts are correct and the ordering they enforce (01 before
02) is real — the Console needs a healthy Observatory. The defect is that the ordering is encoded a
second time, in file numbering, instead of being enforced by the code it duplicates.

## D5. `compose:up` / `compose:down` bypass the CLI

```json
"compose:up":    "docker compose -f compose.harness.yml up --build",
"compose:down":  "docker compose -f compose.harness.yml down"
```

These are a fourth operator surface, and the only one that **skips `requireDocker()` and the workspace
resolution** in `observatory-cmd.mjs`. `compose:up` cannot supply `HARNESS_REPO_ROOT` or
`HARNESS_AGENT_ROOT`, both of which the compose file marks required (`:?`), so it fails with a compose
interpolation error rather than the CLI's message naming the missing variable.

**What a fix has to solve.** Delete both, or make them `node packages/harness-cli/src/cli.mjs
observatory up|down`. A convenience alias is fine; a second lifecycle implementation is not.

## D7. `install.sh` re-creates the legacy product-state path

**Severity: high — it is the one entry that can silently produce a wrong registry.**

```bash
mkdir -p "$ROOT/.harness"
if [[ ! -f "$ROOT/.harness/workspace.json" ]]; then
    printf '%s\n' '{"version":1,"defaultProjectId":null,"projects":[]}' > "$ROOT/.harness/workspace.json"
fi
```

`install.sh:13-15`. But product state does not resolve there:

```js
export function productStateDir() {
    return process.env[PRODUCT_STATE_ENV] || defaultProductStateDir();   // → ~/.harness
}
```

`packages/harness-foundation/src/workspace-store.mjs:36-38`. And the repo-local path is not merely
unused — it is the path the design **deliberately migrated away from**:

- `packages/harness-cli/src/workspace-env.mjs:79` — *"Note what is *not* set here any more:
  `HARNESS_PRODUCT_STATE_DIR`. It used to be forced to…"*
- there is a `migrateLegacyProductState()`, and `qc/state-isolation.test.mjs:157` asserts the legacy
  file **still exists** after migration — it is a copy, not a move.
- `documents/03.state-and-contracts/01.state-layout.md` puts product state at `~/.harness` and states
  that a repo-local `.harness/harness.db` is *"deliberately not honoured"*.

Observed divergence on this machine, which is the proof that the two files are not the same fact:

| File | Size | Contents |
|---|---|---|
| `.harness/workspace.json` (repo) | 954 B | 3 projects: `x79`, plus `e2e` and `final` pointing at `/tmp/…` fixtures |
| `~/.harness/workspace.json` | 404 B | the live registry |

The repo copy holds **test fixtures**. So `install.sh` guarantees the file exists, a test run then
populates it, and nothing ever reads it — while `install.sh`'s output ("Cài xong") implies the registry
is initialised. When the real `~/.harness/workspace.json` is missing, the failure surfaces later and
somewhere else.

**What a fix has to solve.** Delete the three lines. If install must seed state, seed
`productStateDir()` — import the resolver rather than hardcoding a path, which is the same mistake
`workspace-env.mjs` was fixed for. And decide explicitly what happens to the legacy repo-local copy: a
`migrateLegacyProductState` that copies but leaves the source is how a stale duplicate outlives its
migration.

**This is invariant E4 in the small.** *"Never put a trusted record under a path that a container and the
host resolve differently."* Here the two paths differ between the repo and the home directory, and
`install.sh` writes the one nobody reads.

## D8. `.dockerignore` excludes far less than it looks like it excludes

```text
.git
.github
node_modules
**/node_modules
packages/harness-observatory/dist
qc
*.md
.env
.env.*
```

Two things to know about this file:

**`*.md` matches only root-level `.md`.** Docker's ignore semantics are relative to the context root, so
`docker/README.md`, `documents/**/*.md` and `docs/*.md` are still sent. The exclusion reads as "no docs
in the build" and means "no root docs".

**Everything not listed is sent.** `documents/`, `docs/`, `docker/`, `scripts/`, `qc/`+`*.test.mjs`,
`.cursor/`, `.harness/`, `compose*.yml`, `harness`, `install.sh` all become build context.

This is not an image-content problem — the Dockerfiles `COPY` explicitly (`package.json`, `bun.lock`,
`packages`, `profiles`), so nothing extra reaches a layer. It is context **transfer and cache-key**
cost: any edit to `documents/` or `docs/` invalidates the context hash for both images, and the repo's
`.harness/` (product state — registry, `tenants.json`, `projects/`) is shipped to the daemon on every
build even though nothing reads it there.

**What a fix has to solve.** Be explicit rather than aspirational: list what to exclude, or narrow each
service's build context. The check that matters is `docker build --progress=plain` showing a small
context — not the presence of a `.dockerignore`, which is a fact people read instead of verifying.

## K. What must not be removed

Recorded because the obvious cleanup — "one script, fewer files" — would cut into the deployment's
reasoning:

- **`docker/observatory.sh` / `.ps1`** — the documented operator entrypoint, and genuinely thin: both
  forward to `observatory-cmd.mjs`. `observatory.ps1` is at full parity with the `.sh` except the `ps`
  alias. Keep both; the platform split is real.
- **`compose.harness.yml`** — the mount table is the deployment contract, and its comments carry
  decisions that cost real data: the consumer is `:ro` because a bind-mounted SQLite DB written from
  macOS into Linux corrupted one; product state is not the checkout because `git clean` used to take the
  registry with it; the ledger rides the product-state mount because `HARNESS_DATA_ROOT` is a *named
  volume* the host cannot see. **Do not "simplify" these.**
- **`scripts/dev-observe.sh`** — not a duplicate of the Docker path. It genuinely differs (Vite HMR on
  `:5190`, `HARNESS_DATA_ROOT=~/.harness/observe`), and it **refuses to run when the Docker Observatory
  holds the port** by inspecting `/health` for `/data/observe`. That guard is the reason to keep it.
- **The root `harness` wrapper** — the documented primary path, and `documents/04.operations/03.cli-reference.md`
  argues the two-tier design (`./harness` vs `harnessctl`) deliberately. Fix D6 inside it; do not
  collapse it.
- **`docker/README.md`** — despite its defects, it is the only place the operator mount/ledger reasoning
  is written for a reader who is not debugging. Correct it; do not delete it.

## Target shape

Today: **four surfaces**, hand-synchronised.

```text
./harness  ──┬─→ docker/console.sh   ─→ console-cmd.mjs      ─→ compose.console.yml
             │   docker/console.ps1  ─→ (own commands, drifted: D1, D2)
             └─→ cli.mjs observatory ─→ observatory-cmd.mjs   ─→ compose.harness.yml
docker/observatory.sh|.ps1 ─────────→ observatory-cmd.mjs
docker/process/00..03 ──────────────→ observatory.sh, harness, curl
npm compose:up|down ────────────────→ docker compose (direct, unaudited: D5)
```

After D1–D5:

```text
./harness ──┬─→ console-cmd.mjs     ─→ compose.console.yml
            └─→ observatory-cmd.mjs ─→ compose.harness.yml
docker/console.sh|.ps1 ─── forward ─→ console-cmd.mjs      (lifecycle only; surface lives in Node)
docker/observatory.sh|.ps1 ─ forward → observatory-cmd.mjs
docker/README.md ──── the sequence, once, with the tenant check inline
```

The property to reach: **the command surface is defined in `*.mjs` and the shell scripts are transport.**
Then a new subcommand cannot exist on one platform only, and D1/D2 become impossible rather than fixed.

## What this register does not claim

- **No Dockerfile or compose change is proposed.** The images build, the mounts are correct, and the
  mount comments encode two incidents. Image build time and layer sharing were not measured, so
  "two images duplicate `node_modules`" is a suspicion, not an entry.
- **The Windows path was read, not executed.** D1 and D2 are established from the parameter sets and
  source, which is sufficient to prove the surface differs — but nothing here was run on Windows.
- **`console.ps1 start` is fine** (`console.ps1:112` maps it to `up`), so a Windows operator typing
  `start` is unaffected by D1.
- **Nothing here is on the ingest path.** If you are chasing a data defect, this document is a detour.
