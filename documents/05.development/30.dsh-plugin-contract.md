# 30 — Hợp đồng plugin DSH (đọc từ runtime 0.2.1-rc.2)

> Nguồn: `app.asar` của **DeepSeek Harness 0.2.1-rc.2** đang cài trên máy này, đọc read-only bằng
> mmap. Đây **không** phải docs — docs 0.2.1 đã sai hai điểm (xem §3). Ghi lại vì mọi thứ dưới đây
> là hợp đồng thật mà adapter phải khớp, và vì cách kiểm chứng lại không cần quota.

## 1. Hợp đồng

```js
// plugin: { name, inject, apply(ctx) }, đăng ký bằng ctx.plugin(...) — ví dụ ArchivedSessionGate
export const MyPlugin = {
    name: 'harness-eso',
    inject: ['sessions'],
    apply(ctx) {
        ctx.on('agent/pre-step', (payload, next) => /* Decision | Promise<Decision> */);
    },
};
```

| Thành phần | Giá trị thật |
|---|---|
| Hook | `agent/pre-step` |
| Payload | `{ agent, messages, step, signal }` |
| `next()` | **trả** `decision` (`await next()`); không truyền decision vào |
| Decision | `{ kind, messages }`; `kind: 'reject'` ⇒ loop kết thúc bước là `blocked`, **không gọi model** |
| Chèn context | chèn **message** vào `decision.messages`, ngay sau message cuối đã được step "claimed" |
| Source của message | `{ kind: 'agent-instructions', form: 'instructions', changes: [] }` |
| Tool result | hook riêng `tools/result`; `additionalContexts` nằm trên **kết quả tool**, không phải decision |

Message do host dựng bằng `createUserMessage({ content: [{ type:'text', text }], source })`. Hàm này
export từ **`@deepseek-ai/dsh-llm`** (không phải `dsh-agent-instructions` — package đó chỉ định nghĩa
`source.kind = 'agent-instructions'`), và nó **sinh `id`** cho message. Đó là lý do adapter nhận
factory qua `createMessage` thay vì tự dựng object: shape thiếu `id` sẽ bị session store từ chối,
plugin throw thì DSH kết thúc step.

## 2. Enforcement nằm ở đâu

DSH ship sẵn `@deepseek-ai/dsh-hooks-claude-code` **0.2.1-rc.2** ("run a Claude Code hooks.json /
settings hook config on the DeepSeek Harness interception seams"). Vì `harness init profile` đã ghi
`.claude/settings.json`, đường enforcement của ESO trong DSH là **hook pack**, không phải plugin.
Plugin chỉ bơm evidence; `rejectOn` là seam để sau này chặn cứng theo hard blocker.

## 3. Hai chỗ docs 0.2.1 nói sai (đã sửa trong code)

| Docs / bản cũ | Runtime |
|---|---|
| listener `(decision, next)`, gọi `next(decision)` | `(payload, next)`, gọi `next()` |
| thêm `additionalContexts` lên decision | chèn message vào `decision.messages` (source `agent-instructions`) |

Hệ quả của bản cũ: block **không bao giờ xuất hiện** trong context, và không có enforcement nào —
tức là adapter "experimental" thực chất là no-op.

## 4. Kiểm chứng lại (không cần quota, ~5 giây)

```bash
python3 - <<'EOF'
import mmap
p = "/Applications/DeepSeek Harness.app/Contents/Resources/app.asar"
with open(p, 'rb') as f:
    m = mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ)
    for needle in (b"export const ArchivedSessionGate", b"ctx.on(\"agent/pre-step\"", b"agentInstructionsMessage"):
        i = m.find(needle)
        print(needle, "->", i)
        if i >= 0: print(m[max(0, i-200):i+400].decode('utf-8', 'replace'))
EOF
```

Không dùng `grep -a` với `.\{100\}` trên file 182 MB: regex backtracking, mất >60 s.

## 5. Còn thiếu

- Chạy bundle trong DSH thật (cần quota): cài bundle `dsh bridge`, 1 turn, `verify host --require-native`.
- Bundle cần một entry Cordis (đóng gói adapter thành 1 file, import `createUserMessage` từ
  `@deepseek-ai/dsh-llm` rồi truyền làm `createMessage`). Điểm chưa kiểm được offline: loader của DSH
  resolve row `name` trong patch tương đối thế nào — phải chạy thật mới biết, không đoán.
- `rejectOn` nay mặc định `rejectOnHardBlockers`; blocker đến từ check đã khai (`checks.migration` …).
- Mỗi reject ghi `~/.harness/eso-blockers.jsonl` (append-only, product state) **trước** khi trả
  `{kind:'reject'}` — vì hợp đồng reject không mang lý do.
- Blocker chưa vào `buildTurnVerdict` — TurnVerdict vẫn chỉ có sufficiency/score.
