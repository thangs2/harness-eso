# 31 — harness-eso như một plugin DSH (package, không patch DSH)

> Ràng buộc mày đặt ra, ghi thành luật cho mọi việc sau:
> **1)** DSH là hộp đen — không sửa, không touch code DSH. **2)** harness-eso là plugin — phải đóng gói
> được thành package. **3)** Cài bằng **Plugins → harness-eso** trong DSH, không sửa profile bằng tay.
>
> Trạng thái: **P0 + P1 đã giao** (2026-10-22) — xem §8; P2/P3 còn lại. Nguồn: package `@deepseek-ai/dsh-hooks-claude-code@0.2.1-rc.2`
> (đọc từ tarball) + `app.asar` 0.2.1-rc.2, chỉ đọc.

## 1. Vì sao đường cũ sai (không phải vì code sai)

Đường cũ: bundle của ESO **trỏ** tới `@deepseek-ai/dsh-hooks-claude-code` (một package không có trong
`app.asar`). Row chỉ là một dòng `name:`; package đó phải được cài vào profile, và nó kéo theo
peerDependencies là các package **app đã ship**. Kết quả: hai instance `dsh-tools` ⇒ `Symbol()` khác
identity ⇒ mọi tool call chết ở `.prepare()` (ATF-OPS-001, `30 §7`).

Bài học không phải "đừng cài plugin", mà là: **plugin không được kéo bất kỳ package nào mà app đã ship**.
Điều đó chỉ đúng nếu plugin **tự chứa** (zero dependency) và **không import `@deepseek-ai/*`**.

## 2. Hợp đồng plugin DSH — những gì đã kiểm chứng

Plugin = `{ name, inject?, apply(ctx, config) }`. `ctx.on(event, handler)` với `next()` trả decision.
Bảy điểm can thiệp, đọc trực tiếp từ bridge (cùng API công khai, không phải API nội bộ):

| Điểm | Payload | Trả về | ESO dùng để |
|---|---|---|---|
| `agent/created` | `{agent, source, signal}` | — | ghi nhận session (evidence) |
| `agent/pre-step` | `{agent, messages, turn, signal}` | `{kind:'reject'}` hoặc `next()` (decision `kind:'enter'` + `messages`) | chặn prompt / bơm context |
| **`tools/pre-execute`** | `(exec, next)`; `exec.name`, `exec.arguments`, `exec.agent` | `{kind:'deny', reason}` · `{kind:'ask', reason}` · `next()` | **guard write/shell — enforcement thật** |
| `tools/post-execute` | `(exec, result, next)` | `{kind:'block', feedback:[{type:'text',text}], additionalContexts}` | hint sau tool |
| `agent/turn-stopping` | `{agent, turn, signal}` | — | chốt turn, ghi evidence |
| `subagent/start` · `subagent/end` | `info` | — | attribution |

Hai chỗ adapter hiện tại của ESO **sai** (đã lộ khi đọc bridge):

1. `agent/pre-step` payload có `turn`, **không phải** `step`; decision của host là `kind:'enter'`, không
   phải `'continue'`. Chỉ được thêm message khi `downstream.kind === 'enter'`.
2. Bridge **append** message vào cuối `downstream.messages` (`[...downstream.messages, ours]`), không
   chèn "sau message cuối đã claimed" như `cordis.mjs` đang làm.

## 3. Kiến trúc đích

```
packages/harness-eso-dsh/            ← package mới, ZERO dependency
  src/plugin.mjs                     ← { name, inject, apply(ctx, config) }
  src/guards.mjs                     ← tái dùng path-policy/shell-writes/consent từ foundation
  dist/eso-plugin.mjs                ← build self-contained (bun build, 0 external import)
  cordis.patch.yml                   ← insert row: name: harness-eso-dsh/plugin
  package.json                       ← exports ./plugin; dsh.bundle.patch
```

Luồng cài: **Plugins → install bundle → chọn `@mu/harness-eso-dsh`** → DSH link package (không có dep
nào để pnpm cài) → row `harness-eso-dsh/plugin` active → không reboot profile bằng tay.

Vì sao an toàn: plugin chỉ import `node:*` (sau khi bundle) ⇒ **không có đường nào** để pnpm hoist
`dsh-tools`/`dsh-llm`. Bất biến ATF-OPS-001 được bảo vệ bằng cấu trúc, không bằng lời dặn.

## 4. Map năng lực ESO → điểm can thiệp

| Năng lực ESO hiện có | Điểm DSH | Ghi chú |
|---|---|---|
| `guard-shell` (shell writes → path policy) | `tools/pre-execute` khi `exec.name` là bash/pwsh | trả `{kind:'deny', reason}` — reason model thấy |
| `guard-write` (Write/Edit vào path bảo vệ) | `tools/pre-execute` khi `exec.name` là write/edit | cần đọc `exec.arguments.path` |
| consent (`ask`) | `tools/pre-execute` → `{kind:'ask'}` | tương đương HIL của DSH |
| `post-tool-hint` | `tools/post-execute` → `{kind:'block', feedback}` | hint không chặn |
| preflight + evidence gap | `agent/pre-step` | reject chỉ khi **hard blocker** |
| hard blocker (`eso.checks`) | `agent/pre-step` reject | mang `eso-blockers.jsonl` |
| route trace / ledger | `agent/created`, `agent/turn-stopping` | ghi product state |
| observe plane | không đổi (REST/observatory) | ngoài DSH |

**Điểm mất so với hook pack:** hooks `.claude/settings.json` trỏ tới `harness-hook.mjs` (process con,
fail-open nếu node lỗi). Plugin in-process: nhanh, nhưng một exception trong `apply` sẽ làm hỏng bước —
nên mọi handler phải `try/catch` và fail theo hướng đã chọn (B1: không quyết được thì deny, nhưng chỉ
ở kênh write/tool, không làm chết turn).

## 9. Vòng cài đặt thực tế (đo 2026-10-22)

**UI Plugins không có "chọn local"** — trang đó cài từ *spec Host đọc được* (registry), và
`harness-eso-dsh` chưa publish nên gõ tên sẽ báo not found. Đường cài local được **chính docs trong
`app.asar`** chỉ định: `plugin_manager { action:"install_bundle", target:"<absolute package dir>" }` —
cùng installer mà UI gọi, không sửa DSH.

| Bước | Kết quả đo |
|---|---|
| `install_bundle` absolute dir | `application: applied`, `warnings: []` |
| `list_plugins` | `include:harness-eso`, module `file:///…/@mu/harness-eso-dsh/dist/eso-plugin.mjs`, `fiberPhase: active` |
| `doctor dsh` | `healthy`, 1 dep `link:`, không symbol-bearing |
| Sửa code plugin | **HMR không reload bundle** ⇒ `remove_bundle` → bump version → `install_bundle` |
| Row spec | tên **tương đối** `./dist/eso-plugin.mjs` (anchored beside patch) ⇒ không phụ thuộc resolve tên package |

**Ba false positive do chính gate bắt tác giả, đã sửa và có test:**

1. Heredoc ghi path **tương đối** bị coi là "write không resolve được" ⇒ giờ đánh giá bằng literal
   tương đối; chỉ redirect/`tee` không resolve mới deny.
2. Chữ **`tee`** trong commit message bị coi là redirect ⇒ `tee` chỉ tính khi là lệnh (`| tee`, đầu
   dòng, sau `;`/`&`).
3. **`=>`** trong `node -e` bị coi là `>` ⇒ bỏ qua `>`/`>>` khi thuộc `=>`, `->`, `<>`, `2>&1`.

Bằng chứng sau khi sửa: commit `fc000ef` chứa cả `=>` trong message và chạy qua gate bình thường.

**Việc còn lại để chứng nhận end-to-end:** một prompt trong workspace `atrievefin` ghi vào
`AGENTS.md` (gated) ⇒ kỳ vọng `ask`/approval; ghi vào file thường ⇒ đi qua. Sau đó P2: hard blocker +
`agent/pre-step` reject + trail `eso-blockers.jsonl`.

## 10. Ba kết luận đo được sau khi cài thật (2026-10-22)

**a) Không cần atrievefin.** Plugin là **một row trong profile**, không gắn với repo nào. Để chứng minh
chỉ cần một consumer tạm (`/tmp/eso-gate-fixture`: `harness.config.json` +
`.harness/decision-policy.json`). atrievefin chỉ là consumer duy nhất đang có trên máy — không có dòng
code nào của ESO trỏ tới nó.

**b) Product state không phải lời khai consumer.** `harness-eso` có `.harness/` (workspace.json,
registry.json, control.pid) nhưng **không** có policy ⇒ trước đây bị coi là consumer và gate chặn chính
lệnh của tác giả. Giờ consumer = có `harness.config.json` **hoặc** `.harness/decision-policy.json`.
Đo lại: repo harness-eso → không ý kiến; fixture → bị gate.

**c) `ask` không phải gate.** Trên DSH, một quyết định `ask` đi qua (ghi vào path gated thành công) —
đường approval thuộc permission preset của host, không phải của ESO. Vì vậy **mặc định là `deny`** cho
tier `ask` và `gated` không có consent, kèm lý do hướng dẫn; muốn uỷ quyền cho host thì
`config.askMode: "host"`.

Đo live với `@mu/harness-eso-dsh@0.1.7`:

| Ca | Kết quả |
|---|---|
| `write` vào `secrets/b.txt` (locked) | `deny`: "secrets/b.txt is locked by the consumer's path policy (locked tier)" |
| `write` vào `notes/y.md` (gated, không consent) | `deny`: "gated and has no live approval … set askMode=host" |
| `write` vào file không thuộc tier | đi qua |

**Gap còn lại (nói rõ):** kênh **shell** chỉ gate được khi target đọc ra được — tuyệt đối, hoặc literal
tương đối trong heredoc. Lệnh kiểu `> $OUT` / `cd x && > file` không resolve được vì plugin không có
`path` của event và không biết workspace của session (DSH cấp `workingDirectory` service; adapter chưa
inject). Đóng bằng P1.5: inject `workingDirectory` để lấy cwd thật của session.

## 11. P2 đã giao (2026-10-22, plugin 0.2.0)

`agent/pre-step` giờ là **prompt gate thật**:

- chỉ chạy khi decision của host là `enter` (không ghi đè quyết định đã có);
- đọc `eso.checks` từ policy consumer (hoặc `config.checks` của row / factory);
- `loadCheckInputs` + `hardBlockersFromChecks` → nếu có blocker ⇒ ghi
  `~/.harness/eso-blockers.jsonl` (host `dsh`, `event: agent/pre-step`, `step`, `stem`, blockers,
  errors) rồi trả `{kind:'reject'}`;
- **trail lỗi không làm yếu reject**: ghi hỏng thì log + vẫn reject;
- input check không đọc được ⇒ **không** reject (typo config không được chặn hội thoại);
- không có `eso.checks` ⇒ gate không có ý kiến.

Bundle 35,9 KB, vẫn **0 external import** (import module core bằng path để không kéo `bun:sqlite` qua
barrel). Test: 27 case plugin + 4 build.

**Đo live:** write vào `secrets/c.txt` của fixture vẫn bị deny sau khi cài 0.2.0; `doctor dsh` healthy.
Chứng nhận prompt gate cần một session mở tại workspace consumer — bất kỳ consumer nào, không nhất
thiết atrievefin.

## 12. P1.5 đã giao (2026-10-22, plugin 0.2.1)

Gap shell đã đóng bằng **service thật của DSH**, không đoán: đọc package
`@deepseek-ai/dsh-working-directory@0.2.1-rc.2` → service tên `workingDirectory`, API
`get(session)` trả thư mục tuyệt đối; session lấy từ `agent.session` (payload pre-step hoặc `exec.agent`).

```js
inject: ['workingDirectory'],
const dir = ctx.workingDirectory.get(agent.session);   // /abs/session/dir
```

Root resolution giờ: `config.root` → `session dir` → target tuyệt đối của lệnh → cwd. Nhờ vậy
`echo x > secrets/a.txt` (tương đối) bị chặn đúng trong session của consumer, dù DSH chạy tiến trình
ở thư mục app. Test: 30 case plugin (3 case mới cho session dir), 4 case build; bundle 36,5 KB,
0 external import.

Còn lại: `> $VAR` vẫn không resolve được thành đường dẫn cụ thể (không có event `path` như host pack);
khi có write intent mà không đọc được target thì quyết định là **deny**, không phải bỏ qua.

## 13. Audit trail cho mọi quyết định (2026-10-22, plugin 0.2.3)

Host không ghi lại việc nó chặn tool; nếu ESO không ghi thì "vì sao lệnh này bị chặn" chỉ còn lời kể của
model. Bổ sung:

- `~/.harness/eso-blockers.jsonl` nhận cả `hard-blocker` (prompt) và `tool-deny`/`tool-ask`
  (`tools/pre-execute`) với `tool`, `path` (trong blocker `ref`) và `detail` (lý do);
- record mang `projectId` **của consumer mà gate đã quyết định** — gate trả `root` trong decision,
  recorder dùng lại thay vì đoán từ cwd (đo live: `projectId: "fixture"` thay vì `null`);
- `recordToolDecisions: false` để tắt riêng phần ghi tool (block vẫn xảy ra);
- lỗi ghi **không** làm yếu quyết định.

Bundle 38,0 KB, 0 external import; 34 test plugin + 4 build.

**Kết luận về P3 (bơm evidence vào context):** chưa khả thi trong plugin — evidence đến từ MCP
(docgraph/codegraph/agentmemory) của session, không phải thứ plugin đọc được; tự dựng message
`agent-instructions` đòi shape có `id` do host sinh. Ghi nhận là việc của upstream/hook pack.

## 14. Đính chính (2026-10-22): pipeline 7 bước **không** bị bỏ

Trong phiên này có lúc tao mô tả "pipeline 7 bước đã bị thay bằng preflight → gate → observe". Đó là
**sai**. Sự thật kiểm được:

- Bảy bước vẫn là pipeline vận hành cho host IDE (Cursor / Antigravity / Claude), và vẫn được nối đủ
  hook trong `profiles/host/{cursor,agents}-superset.json` — xem bảng ở
  `profiles/templates/WORKFLOW_GUIDE.md §3`.
- UI vẫn vẽ đúng: `PipelineStepper` có 8 stage `prompt · law · routing · recon · eso · brain · exec ·
  memory`; `RequestDetailPage` render stepper + end-to-end flow + consent + drill blocks.
- Cursor/AGY **vẫn cần** docgraph + codegraph + agentmemory; không có native provider nào cho IDE.
- Cái đổi **chỉ ở bước 4**: cơ chế quyết định chuyển từ ngưỡng score sang tier path + hard blocker. Đổi
  ở bước 3: nguồn bằng chứng chọn bằng dữ liệu (`sources`/recipe), không hard-code.
- DSH plugin là **host bổ sung**: có gate + trail, **chưa có evidence spine** (không chạy preflight) ⇒
  trên Observatory, request DSH trống phần law/recon/brain và quyết định chặn nằm ở tab **Gate**.

Việc tao làm sai: viết lại `WORKFLOW_GUIDE.md` (V3) mà xoá chương pipeline, khiến consumer IDE mất tài
liệu mô tả đúng thứ đang chạy. Đã khôi phục ở §3 của guide.
