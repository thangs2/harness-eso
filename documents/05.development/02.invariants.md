# Invariants

**Read this before changing how data flows.** Every rule below exists because breaking it produced a
real defect in this project. Each one names the failure, so you can tell whether your change violates
the rule or merely looks similar to it.

If you must break one, that is allowed — but only deliberately, with the reason recorded in
`docs/04.standalone-revamp-wbs.md`, because the next reader will otherwise "simplify" it back.

---

## A. One source of truth per fact

### A1. A fact read by two components has exactly one definition

The failure this prevents has happened four times, in four different subsystems, and each time it was
invisible until something contradicted:

| Fact | Second copy | Consequence |
|---|---|---|
| which paths are protected | a regex in the observer's checks | blind to **9 of 19** paths, including `scripts/ci/` — the verifier |
| what a shell command writes | a copy in each guard would have been needed | one detector in the pack, called by the guard instead |
| what a pack requires | `detectGaps` used `?? 0`, the scorer used `Math.max(…, 1)` | score penalised a turn for omitting something its own pack said was unnecessary |
| an id scheme | `mcp_call.id` needed the project; the reader scoped by project | two projects computed the same id; the owner's spend was lost |

**Rule.** If two components must agree about a fact, they import one implementation. If they cannot
import it (different language, different runtime), one **generates** the other's copy at build time —
as `path-policy.default.json` is generated for the Python guards.

**Diagnostic.** Ask "where else is this written down?" If the answer is a second file you would have to
remember to update, it is a defect waiting to happen.

### A2. A registry that is not enforced must say so

`sot` (source of truth) is a **label**. It never denies a write. Source-of-truth and *protected* are
independent axes: the WBS is a source of truth the agent must **maintain**, while the verifier scripts
are not a source of truth and are **protected anyway** — editing the yardstick is how it comes to read
PASS.

Do not derive an enforcement decision from `sot`. That is exactly the conflation the current design
exists to undo (`F46`).

### A3. Tool identity must be resolved, never assumed

Cursor routes every MCP call through one generic tool. Storing the wrapper name made `mcp_call_stats`
report **zero** Brain calls for every turn — 339 calls in one conversation, all recorded as the wrapper.
Resolve the real tool at ingest (`mcpToolLabel`).

Further: a single tool can serve two roles with very different cost, distinguished by a **prompt
prefix**, not by its name. 248 of 588 observed calls of one tool were the reasoning tier. So
classification must read the same input the server reads.

### A4. Usage-ledger join hashes the body the MCP server hashes

The DeepSeek MCP server strips `[BRAIN FLASH]` / `[BRAIN FALLBACK]` / `[pro]` / `[flash]` before it
calls the model, and writes `sha256` of that stripped body into the usage ledger. Hashing the raw
transcript argument (still carrying the prefix) made every Brain call show as `flashBrain ≥ 1` with
`brainUsageCalls = 0` — spend present in the ledger, invisible on the request. Observer join key:
`usageHashPrompt` in `mcp-prompt-store.mjs`, kept aligned with the MCP strip.

### A5. DeepSeek call *counts* come from the ledger, not transcript `tool_use`

Cursor can record an assistant `tool_use` for `ask_deepseek_pro` / flash that never reaches
`postToolUse` or the MCP server (no frame, no usage line). Counting those from `llm_call.tool_names`
showed "DeepSeek Pro" with empty Brain tokens. `mcp_call_stats` Pro / flash / smart buckets are
derived from attributed `mcp_call` rows only — the same ledger that supplies token totals.

## B. The gates

### B1. A guard that cannot decide denies

A guard that silently stops enforcing is worse than no guard, because the operator believes they are
protected. Overridable per consumer by `guards.unavailable: "deny" | "warn"`.

Telemetry hooks are the inverse — a trace hook that cannot write must **not** break the turn.

**This rule has already caught a real bug.** A consumer guard's outer handler was fail-open unless an
unrelated subsystem was active, so a `NameError` in a new check silently permitted every command. The
same code, after the change, denied with `Hook error (fail-closed)` and made the mistake obvious.

### B2. Records a gate trusts must be unwritable by the gated party

An incident had the agent write its own evidence stamp: `allowWrite: true` where preflight had computed
`false`, a score of `0.85` where the verdict was `0.3667`, and a `hilWaiver` field that **exists nowhere
in the codebase** — the agent invented a governance concept to record a human approval.

Trusted records live in **product state**, which both guards deny writes to. The session directory can
never hold one: it must stay agent-writable, because the stamps the gates read are written there.

### B3. Consent opens `ask`, and only `ask`

A locked path is one a human **reserves**, not one they approve. Letting an approval reach it makes the
strongest tier the weakest, since consent is the record a person can produce most casually.

This was written wrongly once — and the comment directly above the code said the opposite of what the
code did. Code and comment disagreeing is itself the signal to stop.

### B4. One approval, both channels — or neither

Consent must be consulted by the write gate **and** the shell gate. Opening one and not the other makes
the approval look broken and teaches the agent to route around it.

The one asymmetry that is intentional: a `gated` path is not writable via shell, because a shell command
carries no evidence. That is a property of the channel, not of consent.

### B5. Every channel that can write must be gated

`guard-write.py` only sees the write **tool**. A shell `cat > path` was an entirely open second channel:
one turn wrote **seven protected files** that way while the harness recorded all of them as **reads**.

When you add a gate, enumerate the channels it must cover. When you add a channel, ask which gates
already exist for the others.

### B6. Absent policy means the safe default; declared means declared

- `paths` absent → the product's default applies. Shipping a feature must never silently remove a gate.
- a tier empty → that tier protects nothing. Explicit, and distinguishable from "unconfigured".
- a declared list **replaces** the default; it does not merge. Merging resurrects a default the consumer
  deliberately removed.

### B7. Cognition and Write are different gates

Preflight evaluates evidence sufficiency to prevent ungrounded generation. But **reasoning (Brain)**
and **writing (Guard-Write)** operate on different invariants:

- **Code implementation**: Brain code-generation without factual baseline (code AST, schemas, coding law)
  produces hallucinations. Dispatcher must close gaps via recon before code generation.
- **Docs, architecture, and analysis**: Analysis is synthesis and deep thinking. The Brain is permitted
  and encouraged to reason immediately to structure solutions, WBS, and RFCs.
- **The actual enforcement gate**: `guard-write.py` enforces attestation and sufficiency at write-time.
  Preflight sufficiency gaps must never prevent Brain deep-thinking on non-code tasks.

## C. Identity and attribution

### C1. Hook events and requests arrive on different clocks

Hooks are written by the IDE **as calls happen**. Requests come from the transcript, which is a **poll**.
So a tool event routinely exists *before* the turn it belongs to has a row.

Consequences to keep in mind whenever you write linking logic:

- A time-based placement is a **guess**. It will sometimes be wrong, and the window it uses is
  minute-rounded, which straddles turn boundaries.
- A guess must be **correctable**. The original rule only filled missing values, so a wrong guess was
  permanent — **3,438** events across 7 conversations ended up filed under the wrong turn, and a turn
  that made 19 tool calls displayed 2.

### C2. An event's own generation is authoritative

It is first-hand evidence; a time window is inference. It may **overwrite** a previous assignment, which
is safe precisely because `linkRequests` guarantees exactly one request holds any real generation.

Any correction update must be a **no-op when values already match**. Otherwise it reports a change every
cycle, and the change gate forces a full recompute forever.

### C3. A timestamp-derived value must not be trusted as identity

`request.started_at` is minute-rounded from the transcript's human-readable timestamp. It cannot
distinguish two turns inside one minute. Use it for ordering and windows, never for identity.

### C4. A placeholder must be distinguishable from a real value

When no real generation is captured, the row is stamped `generation_id = id` so the spine still has a
join key. Written into the same column the link guard reads, this made every prompt match impossible —
and emptied the rules table for the entire project.

Two rules follow:

- Write a placeholder **last**, after real matching has been attempted.
- Never test `IS NOT NULL` to mean "has a real link". `hasRealGenerationLink()` is the canonical form.

### C5. A cursor is a claim about bytes, not a position

`size < last_offset` catches truncation but **not** an in-place rewrite to an equal-or-longer file. In
that case the offset lands in unrelated text, the prompt before it is never read, and the cursor
advances anyway — a permanently lost turn. Prove the bytes before the cursor are the ones consumed
(seam hash), and keep a repair command for cursors that predate the proof.

### C6. A write-free record is proof a handler did not run

The MCP server writes its usage ledger in an unconditional `finally`. Therefore **an absent record
proves the handler never executed** — which is what makes "dispatched but vanished" localisable to one
side of the pipe. Do not move that write inside a conditional; the diagnostic value depends on its
unconditionality.

## D. Measurement and display

### D1. Do not merge measurements with different owners

The IDE's `stop` hook reports the **dispatcher's** tokens. The MCP server's ledger reports the
**Brain's**. A Cursor turn's cost is mostly in the second, and no single channel reports both.

Merging them into one "turn cost" produces a number nobody measured. Display them separately and say
which is which.

### D2. Two quantities that share a transport must not share a label

Model calls and tool calls both travel over MCP and share **nothing else**: different counts, different
costs. Labelling the model figure "MCP calls" meant a turn with five Jira calls displayed no MCP
activity at all.

### D3. "Absence of evidence" is not "evidence of absence"

A check that cannot see must report **cannot determine**, not a clean result. `brain-before-protected-write`
once reported *"no protected path was edited"* for a turn whose edited files were on disk under a
different turn — a claim about the filesystem drawn from data that says nothing about it.

The corollary for the UI: a skipped check carries a heuristic flag so it is not read as a pass.

### D4. Zero and unknown are different

`brain_prompt_tokens` is **NULL** when nothing reported, never `0`. A gate that reads "unknown" as
"nothing spent" understates cost; a gate that reads it as "zero" makes an unreported turn look cheap.

### D5. Do not invent a number

Input tokens are **not derivable** from a transcript. The model's input is the whole context — system
prompt, attached rules, open files, history, tool results — and only a hook payload reports it. An
earlier fallback reported the user's own prompt length ÷ 4 as "input", which rendered as a real
measurement: `9` next to `628` out. Report unknown as unknown.

## E. Performance

### E1. Never block the HTTP thread on a database write

The ingest runs in a **child worker process**. When it ran on the server's own thread, a synchronous
SQLite write froze the monitor — and the monitor failing while you work is when you need it.

### E2. Skip derived work only when nothing that feeds it changed

The change gate is the reason a poll and thousands of historical turns can coexist. It is also a trap:
**anything that changes derived meaning must participate in it.** A re-attribution changes a turn's
files, tools and checks; a migration changes everything. Both are wired into the gate, and both were
added after a fix appeared not to work.

### E3. Read tails, not files

Transcripts and the MCP ledgers grow without bound, and some of them are read on **every guarded write**.
Read from an offset or a bounded tail slice.

### E4. Consumer and product state are different failure domains

Product state is on a named volume in Docker and a home directory on the host. Never put a trusted
record under a path that a container and the host resolve differently — that is how a feature works
locally and silently does nothing in production.

## F. Boundaries

### F1. Never provision the product repo

Provisioning writes agent hooks. Writing them into the repo that ships them is a loop, and the planner
refuses a root inside the product checkout.

### F2. A hook may import only the sandboxed foundation entry

Hooks run on a consumer with no installed dependencies. `@mu/harness-foundation/pure` is the sandboxed
subset; the package root drags in a database driver and a runtime-conditional import that no consumer
can resolve. The pack build asserts this.

### F3. The injected artifact must have no external imports

The pack is a **bundle**, and its build fails if it imports anything outside `node:*`. This is the
invariant that keeps the consumer independent of the product checkout — the previous design had the
consumer's guards spawn code out of the checkout, so a `git clean` in the product repo broke every
consumer's guards.

### F4. The consumer is read-only to the product

A bind-mounted SQLite database written from a host into a container is what corrupted one. The consumer
is an input.

### F5. Cursor hooks cannot ask a human

The hook contract accepts only `allow` and `deny` — verified from the shipped bundle, which warns that
`ask` "is not yet implemented". Anything that looks like "prompt the human" is a deny with a message, and
a real approval flow must live outside the hook (Console + product state).

## G. Change discipline

### G1. Migrations are append-only

Never edit an applied migration; it has already run on other machines. To change what a derived table
means, clear it in a new migration and let the corrected code rebuild it.

### G2. A regression test must fail when the fix is reverted

Verify it: restore the bug, watch the test go red, restore the fix. A test that passes either way
documents nothing.

### G3. Measure, do not assert

Every claim in the defect log should cite a count, a command output or a file. "Seems fixed" is not an
entry, and the difference is what makes a fix reviewable.

### G4. A comment states why, and which failure

The comment density in this repo is a convention. A comment that restates the code is noise; a comment
that carries the failure which produced a non-obvious rule is what stops the next reader from removing
it.

**Enforced since H5 (2026-10-21):** a consumer that declares `harnessSurface` in
`harness.config.json` fails `harnessctl verify host` when an editable glob matches a hook config the
host runs, or when always-on files exceed `alwaysOnMaxTokens` (default 8000). Before H5 the invariant
was only a prose rule; a harness-optimizer surface (Harness² declares `.codex/hooks.json` editable)
would have satisfied H0–H4 while letting the optimizer delete the guard.
